这台手机上同时跑着十几个 AI 会话，分别对应不同项目：一个在调 ESP32 工具链，一个在啃《我的世界》服务端的符号表，一个在做 Android 打包，一个在写 Vulkan layer。它们共享同一个文件系统，但互相看不见对方聊了什么。

结果是：**经验散在各自的对话里**。同一个坑，A 会话踩过并修好了，B 会话三天后从零再踩一遍。

我想把这些经验汇成一份清单，再去发博客。这篇记的是做法，以及一个让我改变想法的插曲。

## 一、先说结论：通信比编排便宜

一开始想到的是"智能体团队"那套：建成员、派任务、维护任务板与 write scope、等交付。但我要做的事本质是**问经验**，不是**派任务**。

| 维度 | 派任务 | 问经验 |
| --- | --- | --- |
| 关系 | 上下级 | 对等 |
| 需要的状态 | 谁在跑、谁卡住、谁该收尾 | 无 |
| 交付保证 | 有（任务板可见） | 无（回不回随它） |
| 成本 | 建成员、维护上下文、回收 | 一次发消息 |

所以我写了一个很薄的插件：只能列会话标题与可用状态、给某个会话发一条消息。**看不到对方的对话记录**，也不做任务管理。就这些。

## 二、怎么问：四段式 + 强制标注

早期我问的是"你踩过哪些坑"，回答质量参差。改成固定模板后好很多：

```
【症状】一行，尽量是别人会搜到的那句话
【原因】一两句
【修法】可执行的命令或步骤
【范围】只在这台设备 / aarch64 通用 / 所有 Termux 都适用
```

两个细节值得说：

**一是"症状要写成别人会搜的那句话"。** 这条要求把"我踩了个坑"变成"搜索命中"。`aapt2: Exec format error` 能被搜到，`构建失败了一下` 不能。

**二是要求标注验证状态。** 用词是"实测 / 今天实测 / 记忆中的结论"。事后证明这是整件事里最重要的一条约束——下面那个案例就是靠它抓住的。

## 三、结果：十类，四十余条

四个会话各报 6 条，加上我自己这几天撞的，汇成了十类：

构建 · 容器 · 网络 · 工具链 · Node/pnpm · 权限与系统调用 · glibc 在 Android · 逆向与二进制 · NDK 交叉编译 · Android 构建

其中有几条是**机制层面的硬限制**，不是"换个配置就行"：

- 新 Android 的 seccomp 对 `set_robust_list` 是 **KILL**，不是返回 ENOSYS——所有 glibc 程序一启动就死，chroot/proot 都躲不掉
- Android SELinux 禁止 app 数据目录 `link(2)`，所以交叉工具链解压后大量 gcc 硬链接失效；7z 更糟，**静默跳过**
- box64 把代码 JIT 进匿名映射，所以在它上面打 inline hook 从原理上无效

这些写进清单后，价值立刻体现：下次我或别人遇到 `Unknown signal 31`，不用再花一天。

## 四、插曲：我写进博客的结论是错的

清单整理完，我发了两篇博客。其中一篇里我写：

> aapt2 是 x86-64 的，AGP 从 Maven 拉下来在 ARM 上跑不了。

看起来很有道理，因为我自己确实踩过这个错，也确实靠 `aapt2FromMavenOverride` 解决了。

后来 EFML4A 那个会话回了我六条，其中一条是：

> **"aapt2 / build-tools 在 arm64 跑不了"是过时结论。**
> 真正跨架构的是 NDK 的 prebuilt 工具链，不是 build-tools：build-tools 36.0.0 的 aapt2 实测是 aarch64 ELF，Termux 自带 aapt2 也是 aarch64；d8 是 jar，本来就跨架构。
> ⇒ 先 file 判定，别先换工具链。

我当场 `file` 验了一遍——**它是对的**。

于是真实情况是两件事叠在一起：

| 事实 | 后果 |
| --- | --- |
| 本地 build-tools 里的 aapt2 确实是 ARM | 直接调用没问题，"必须 x86-64"的说法是错的 |
| 但 AGP 默认从 Maven 拉 x86-64 的 aapt2，无视本地 SDK | 所以仍然必须设 `aapt2FromMavenOverride` |

我的结论"方向对、表述错"：需要配置是真的，把原因说成"aapt2 只有 x86-64"是假的。博客已改，标题从「aapt2 是 x86-64 的」改成「aapt2 的架构问题」，正文先纠正误区再讲配置。

顺带同一批还改了另一处：我原来写「给 `/dev` 挂 tmpfs 再 mknod 就修好了」，但实测只能救 `/dev/null`——`/dev/urandom` 读取仍是 `Permission denied`，要另写 `LD_PRELOAD` shim。

## 五、真正起作用的是交叉验证，不是"多问几家"

这件事让我把流程改了一处：

- 之前：多个会话都给结论 → 取交集/取多数
- 现在：多个会话给结论，**凡是有条件复现的，一律自己复现一遍**

"多问几家"不产生正确性，只产生覆盖率。四个会话如果都基于同一种误解，交集反而是错的。上一条 aapt2 的错误就是我自己写的，问三家也不会有人纠正——直到有人真的 `file` 了那个文件。

所以模板里的"【范围】"和"标注验证状态"不是形式：它们决定了哪些结论可以直接用、哪些必须复核。

## 六、什么时候该用编排

这套办法有明确的失效边界：

| 场景 | 该用什么 |
| --- | --- |
| 问经验、取结论、交叉验证 | 对等消息（本文） |
| 有顺序依赖的任务 | 任务板 / 团队 |
| 多人写同一批文件 | 团队（write scope 才能防冲突） |
| 需要"谁没交"可见 | 团队 |

我这次全是"问"，没有"派"，所以对等消息够用。如果我下一步要让它真去改代码，就必须有 scope 与交付追踪——那时候薄插件不够。

## 七、落地：结果进仓库，博客只做索引

清单放在 [termux-env-archive/TROUBLESHOOTING.md](https://github.com/moyingyilang/termux-env-archive/blob/main/TROUBLESHOOTING.md)，博客只写叙事与索引。

理由很实际：**博客搜不到报错原文**（我的文章标题里不会写 `Unknown signal 31`），而仓库里的 Markdown 能被 grep、能被搜索引擎索引、能被 diff。清单会持续更新，博客发出去就不再改。

一件小事：清单里每条的标题就是那句报错。这样别人搜报错，能直接落到条目上。
