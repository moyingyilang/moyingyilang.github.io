主项目是一套 Kotlin + Compose Multiplatform 的客户端，Android 与桌面（JVM）两端共用同一套 UI 代码。
桌面另开一条 C++/Qt 的原生实现线，理由是体积、启动与内存：JVM 那套要自带运行时，打包链也长。

"一对一复刻"听起来是写代码的问题——界面就在那里，照着实现就行。

真动手才发现，第一个要回答的不是"怎么写"，而是：

- 到底有多少个屏？
- 有多少个组件？
- 哪些是死代码？
- 哪些效果 Qt 根本给不了？

这些都是清点问题，不是编码问题。这是这个系列的第一篇，只讲清点。

## 1. 为什么先清点

| 风险 | 直接开写的后果 | 清点怎么解 |
| --- | --- | --- |
| 照着印象写 | 复刻的是记忆里的界面，不是代码里的界面 | 每条结论都落到 `文件:行号` |
| 漏屏 | 两端各有一套导航，凭印象必然漏 | 两端各自枚举目的地，再合并去重成逻辑屏幕 |
| 把死代码搬过去 | 移植量凭空变大，还带进没人维护的参数 | 每个组件统计调用点，0 处调用的单独记账 |
| 猜"Qt 能不能做" | 做到一半才发现某个效果要换技术栈 | 每个效果给一个四选一的判断 |

清点的口径先写死，否则数字没法比：

| 口径 | 取值 |
| --- | --- |
| 记录范围 | 只写源码里实际读到的；读不到的一律标"未确认" |
| 运行状态 | 未启动模拟器、未启动桌面进程，结论全部来自静态阅读源码 |
| 产出 | 三份文档：屏幕清单、组件清单、效果与动画清单 |

## 2. 清点出来的数字

### 2.1 屏幕：24 个逻辑屏幕

| 计数口径 | 数量 |
| --- | --- |
| 逻辑屏幕（两端合并去重后） | 24 |
| Android `NavHost` 注册的目的地 | 20 |
| 桌面端 `App()` 的分发分支（不含兜底） | 21 |
| 桌面端兜底占位页壳 | 1 |
| 有完整实现、但全工程 0 个调用方的界面 | 1 |

关键点是：24 不是任何一端的数字。两端连导航机制都不一样——Android 用 Navigation Compose
加字符串路由，桌面是手写状态机（`sealed interface` + 字符串 route），没有导航库。
只有把两边的界面按"是不是同一个页面"合并，才能得到一份可以照着施工的清单。

### 2.2 组件：105 个 `@Composable`

| 分类 | 数量 | 说明 |
| --- | --- | --- |
| 设计系统核心 | 23 | 跨屏复用的底座，含两个不是"组件"的入口（形状函数与主题入口） |
| 屏幕级 public | 27 | 18 个页面入口 + 9 个可复用组件（对话框、浮钮、选择器） |
| 屏幕内 private | 55 | 只在本文件被调用，但 Qt 侧仍然要逐个重建 |
| 合计 | 105 | |

统计过程本身踩过一个坑：直接数 `@Composable` 注解会数到 130 处，多出来的 25 处是
`content: @Composable () -> Unit` 这类 **lambda 类型标注**，不是组件。
所以"105"这个数必须连着口径一起写下来，不然换个人重数就会对不上。

另有 3 个不属于 `@Composable`、但属于组件层的扩展与类：列表条目动画的两个重载，以及一个超椭圆形状类。

顺带得到的一条清单：图标只有 Material Icons Extended 一族，共 47 个不同图标，
全部是代码里的矢量图、没有图标字体。Qt 侧要逐个找对应字形；带 `AutoMirrored` 的那几个还要按排版方向手动镜像。

### 2.3 按行数排，最大的是这三个屏

| 文件 | 行数 | 入口 | 为什么重 |
| --- | --- | --- | --- |
| `screens/detail/DetailScreen.kt` | 1316 | `:527` | 一个 `LazyColumn` 里 13 个分区，5 个操作各有独立登录门 |
| `screens/profile/ProfileScreen.kt` | 1293 | `:119` | 全部设置项 + 签到日历 + 壁纸 + 风格预览 |
| `screens/reader/ReaderScreen.kt` | 1127 | `:284` | 两种阅读形态 + 缩放 + 预取 + 三档比例回退 |

三个文件合计 3736 行，占 `ui/` 目录 Kotlin 代码总量（15036 行）的约四分之一。
"先挑几屏做"如果按直觉挑，很容易挑中这三个里的一个，而它们的复杂度并不代表其余屏幕。

### 2.4 效果与动画：42 项判断

| 类别 | 数量 |
| --- | --- |
| 视觉效果（E01–E23） | 23 |
| 动画（A01–A19） | 19 |
| 合计 | 42 |

每一项都给了四个判断之一，分布如下：

| 判断 | 含义 | 数量 |
| --- | --- | --- |
| (a) | Qt Widgets + QSS 能表达 | 8 |
| (b) | Widgets + QPainter 自绘能表达 | 25 |
| (c) | Qt Quick/QML 更合适或必须 | 5 |
| (d) | 四个栈都做不到 | 4 |

这张表改变的是架构判断，不是心情：

- 这套视觉的主体是**自绘**，不是"Qt 特性"。(b) 占 25/42，QSS 只够撑 8 项纯色、描边、单层渐变。
- **只有 Qt Quick 能做的有 2 类 4 条**：物理弹簧参数化的动效 3 条，列表条目增删位移动画 1 条。
  Widgets 只有解析曲线，没有弹簧积分器；`QListView` 也没有条目级布局动画。
- **四个栈都做不到的 4 项**：系统栏图标明暗、真 backdrop-filter、动态取色、系统级预测性返回跟手。
  逐表面背景模糊在主项目里本来就只是近似（模糊整块底图 + 半透明填充）；另外三项依赖平台接口，桌面端没有对应输入源。

## 3. 清点之后，施工顺序变了

原计划是把 24 个屏横向铺开，先把屏数凑齐。清点之后改成**先做核心阅读路径**：

| 路径 | 依据 |
| --- | --- |
| 首页列表 | 所有入口的起点；几十张封面同时在滚，占位与加载态是观感底线 |
| 详情 | 单文件 1316 行，13 个分区，5 个需要登录的操作 |
| 阅读器 | 1127 行，两种形态，缩放 1x–5x，预取，切片还原 |
| 章节选择 | 两端各有一份实现，每页条数还不一样：Android 10 章，桌面 50 章 |
| 搜索 | 881 行，排序 / 字段 / 年月筛选，外加标签屏蔽提示 |

这样切的理由有三条：

1. 复杂度集中。两个最大文件加上结构最复杂的两页都在这一条路径上。
2. 日常真正在用。剩下的屏幕大多是同一套骨架（顶栏 + 状态分支 + 列表 + 页脚）的变体。
3. 先把它们打穿，等于一次性验证三件最难的事：表面工艺、图片管线、列表性能。

"章节选择每页条数不一致"这类差异，是清点才暴露出来的：它必须在写代码之前定死，
否则 Qt 侧会照着其中一端的实现抄，另一端的用户立刻能看出不对。

## 4. 清点顺手排掉的坑

### 4.1 三个 0 处调用的组件不要搬

| 组件 | 位置 | 状态与处置 |
| --- | --- | --- |
| `GlassCircle` | `ui/components/Glass.kt:262` | 圆形玻璃表面，注释说给头像与图标按钮用，全仓库 0 处调用；不搬 |
| `Modifier.accentBar` | `ui/components/Glass.kt:247` | 左侧强调条，只有定义与测试，0 处调用；不搬 |
| `NoticeHost` | `ui/Notices.kt:61` | Android 侧改用 `SnackbarHost` 显示同一条状态，这份实现是死代码；不搬 |

`NoticeHost` 有个容易踩的细节：桌面端有一份同名同签名的独立实现，而且真的被挂载在应用根部。
所以"两端同名的组件"不能只看名字——要按端分别核对调用点，桌面那一份要搬，Android 那一份不要。

同类还有一处**死屏幕**：桌面端某个页面有完整实现，但全工程 0 个调用方，
真正的入口用的是另一个页面的 `initialTab` 参数。照着页面清单搬，就会多搬一个屏。

### 4.2 没有骨架屏，加它是新增不是复刻

全 `ui/` 目录内搜 `skeleton`、`shimmer`、`骨架`，0 命中。加载态只有三件东西：

| 组件 | 位置 | 形态 |
| --- | --- | --- |
| `LoadingBox` | `ui/components/StateBox.kt:28` | 整屏转圈 |
| `CoverFallback` | `ui/components/ComicCard.kt:265` | 封面位置一块平色底 |
| `PageFallback` | `ui/screens/reader/ReaderScreen.kt:1026` | 阅读页按比例撑高的透明占位 |

也就是说，Qt 侧如果加骨架屏，那是**新增功能**，要单独立项、单独验证，
不能算进"复刻完成度"。这条如果不先写下来，很容易在评审时被当成"没做完"。

### 4.3 九个死令牌别照抄

令牌表里有一批声明了、但全仓库没有任何读点的常量。举三个：

| 死令牌 | 声明处 | 实际情况 |
| --- | --- | --- |
| `Glass.blurRadius = 40.dp` | `ui/theme/Tokens.kt:102` | 只有声明，没有任何读点 |
| `Sizing.hairline = 1.dp` | `ui/theme/Tokens.kt:63` | 描边实际读的是另一个令牌 |
| `JmEasing.decel` / `JmEasing.inOutQuad` | `ui/theme/Theme.kt:50` / `:67` | 两条曲线都未找到读点 |

危害不在于多写几行，而在于它们看起来"是设计系统的一部分"。
照抄进 Qt 的样式表，以后没人敢删，也没人知道该不该读。

还有一类相反方向的坑：有四个排版槽位没有被本项目的排版函数覆盖，落回 Compose 库的默认值，
于是它们**不随风格切换字号**。Qt 侧要么按规格补上数值，要么明确接受这个差异——
两种都行，但不能不知道。

## 5. 清点本身就是交付物

三份清单现在的用法很直接：

| 用途 | 具体做法 |
| --- | --- |
| 复核 | 每条结论都带 `文件:行号`，可以逐条回源码核对 |
| 排期 | 每实现一屏，就对着清单勾掉一屏，进度可数 |
| 划界 | "未确认"与"不存在"单列一节，避免把新增当成复刻 |
| 谈判 | 42 项判断里哪些要引入 Qt Quick，是选型问题，先摆数字再决定 |

一句话总结：把"照着写一遍"，变成"对着清单逐条核"。
下一篇写核心阅读路径怎么落地，以及那 42 项判断里到底先做哪几项。
