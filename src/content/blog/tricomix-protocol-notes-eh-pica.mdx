TriComiX 是一个多内容源阅读器（代码在 [github.com/moyingyilang/TriComiX](https://github.com/moyingyilang/TriComiX)）。
它同时接三种内容源：一个网页站（E-Hentai，下称 EH）和两个 App 侧接口（PicACG 哔咔、JM）。
接口层看起来是同一件事——发 HTTP、解析 JSON 或 HTML——但真正吃掉时间的部分完全不同：

- 网页站的坑在**页面结构**：站点改版一次，选择器就全废，而且失败是静默的（解析出 0 条，不报错）；
- 私有 API 的坑在**请求头与签名**：少一个头、nonce 用错形式，服务端只回一个笼统的失败码。

这篇是两条链路都跑通之后留下的协议笔记。方法、路径、请求头名、选择器全部保留，凭据一律用占位符。

这一节不是免责声明，是方法说明。我做的是**互操作性研究**，不是移植别人的客户端。

## 一、网页站 E-Hentai

### 1.1 域名与用途

EH 不是单一域名，登录态、内容页、图片 CDN 分在不同主机上：

| 域名 | 用途 |
| --- | --- |
| `e-hentai.org` | 主站，公开内容 |
| `exhentai.org` | 需登录的站点，**同一套页面结构** |
| `forums.e-hentai.org` | 论坛，登录入口之一 |
| `ehgt.org` | 缩略图与图片 CDN |
| `ehwiki.org` | 标签维基 |

"同一套页面结构"这一条很关键：解析器只写一份，域名选择交给 `EhHosts` 那类逻辑处理即可。

### 1.2 主要路径清单

| 路径 | 用途 |
| --- | --- |

### 1.3 参照实现的模块划分，与我要写的对应物

参照实现把职责切得很细，我按功能对齐，而不是按类名对齐：

| 参照类 | 职责 | 解析方式 | 我的对应物 |
| --- | --- | --- | --- |
| `EhClient` + `EhRequest(Builder)` | 请求编排 | — | 源内 HTTP 客户端 |
| `EhCookieStore` | cookie 持久化（登录态） | — | `EhCookieJar` |
| `EhHosts` | 域名选择与可用性 | — | 域名选择逻辑 |
| `EhUrl` | URL 构造（详情/收藏/归档等） | — | `EhUrl`（纯逻辑，可单测） |
| `GalleryListParser` | 首页/搜索列表 | Jsoup | `GalleryListParser` |
| `GalleryApiParser` / `GalleryTokenApiParser` | 列表 JSON 接口 / 取 token | JSON | 列表 JSON 分支 |
| `GalleryDetailParser` | 作品详情 | HTML | `GalleryDetailParser` |
| `GalleryPageApiParser` / `GalleryPageParser` | 图片列表与分页 | JSON（含 `hath`） | 页列表解析 |
| `SignInParser` | 登录 | HTML + cookie | `SignInParser` |
| `FavoritesParser` / `EhHomeParser` / `TopListParser` / `ArchiveParser` / `TorrentParser` | 收藏/首页/榜单/归档/种子 | 混合 | 按需实现 |

实现顺序我是这么排的：先把纯逻辑的 URL 构造落地并可测，再做 cookie jar 与客户端，然后列表、详情、图片列表、登录。
理由很直接：**纯逻辑能用自写样本测，网络与解析必须先有真实页面才谈得上验证**。

### 1.4 登录态就是 cookie

EH 没有 token 体系。登录成功后服务端给 cookie，之后每个请求带上即可，客户端只需要做 cookie 的持久化与域匹配。
这条决定了登录解析器的产物：`SignInParser` 主要工作在 HTML 表单与响应 cookie 上，而不是解析一个 JSON 里的 access token。

也正因为是 cookie，**会话重启就没了**：目前实现里 EH cookie 只活在运行内存，重启需要重新登录。

### 1.5 hath：嵌在主机名里，不是查询参数

`hath` 不是加密，也不是签名。它是**服务端随页面下发的参数**，必须与图片 URL 一起原样使用。

这里有一处我自己踩出来的更正。早先我在探针里检测 hath 时按查询参数找，结果显示"含 hath: 假"，我据此以为图片地址里没有它。**这个结论是错的**：

```text
早期检测： url.contains("?hath=")        -> 判为「不含 hath」（误报）
实际形态： https://<随机主机>.hath.network:53342/h/…
```

真实地址形如 `https://<随机主机>.hath.network:53342/h/…`，`hath` **嵌在主机名里**。
取图本身不受影响（地址是原样使用的），但界面与探针上那条显示是误导性的，会让人误以为该字段没被用上。
教训是：**检测一个字段时，先确认它在真实数据里的位置，再写匹配串**——否则"未检出"会伪装成"不存在"。

### 1.6 真实页面结构事实

以下全部抓真实页面核对得到，不是照着参照实现推的：

| 部位 | 事实 |
| --- | --- |
| 列表容器 | `table.itg.gltc` |
| 列表列序 | 分类 / 缩略图+时间 / 标题 / 上传者，共四列 |
| 时间字段 | `postedpop_<gid>` |
| 缩略图与上传者 | **不在标题单元格里**，要按列取 |
| `gl1e` / `gl3e` / `gl3t` / `gl5t` | 属于另一种布局，在真实 `gltc` 页面里出现 0 次 |
| 详情页 `#gj` | 实际为空 |
| 详情页作者 | 在 `/uploader/<名字>` 链接里 |
| 图片页顶部 `<img>` | 是界面图标，不是内容图 |
| 图片页内容图 | 带 `style` 属性 |
| 原图链接 | 在 `Download original` 链接里 |

第一版解析器就是栽在"按单元格取值"上的：搜索能返回结果，但**封面与作者取不到**。
改成一列一列取之后，搜索 25 条结果的标题、封面、作者、时间、页数、标签全部对得上。

### 1.7 分页：gtoken 已失效，改翻缩略图页

作品的图片列表按"页"组织（每页若干张），语义上不同于 App 侧的"章节"。这里的改版最能说明网页站的坑：

| 检查项 | 结果 |
| --- | --- |
| 旧方法 `gtoken`（走 `api.php`） | 请求第 21–23 页与第 1–3 页**都**返回 `{"error":"Invalid page."}` |
| 结论 | 不是页段越界，而是该方法在新版站点**已失效**（与消失的 `showkey` 同类改版） |
| 现行做法 | 翻缩略图页 `?p=N`，`?p=0/1/2` 分别给出第 1–20 / 21–40 / 41–60 页的 imgkey |
| 长作品验证 | 141 页作品：详情页 141 页、token 解析正常、首批内联 20 个 imgkey |
| 修复后 | 走源接口 `pages()`，**141 页全部带 imgkey**，末页取图成功 |

一个刻意的决定：**失效的 `gtoken` 解析器与其测试已经删除**。
留着一份不再工作的代码，等于告诉后来的人"还有另一条路径"——那是比缺失更贵的信息污染。

## 二、私有 API：PicACG

私有 API 的问题反过来：页面结构不会变，但**请求的每一个字节都可能被校验**。

### 2.1 基址与响应外壳

- 基址：`https://picaapi.picacomic.com/`
- 统一响应外壳：`{code, message, data}`，**`code != 200` 一律按失败处理**——不要把 `data` 当成功数据用；
- 分页外壳：`{docs, total, limit, page, pages}`，列表在 `data.comics` / `data.eps` / `data.pages` 下。

外壳统一有好处也有坏处：好处是错误处理集中一处；坏处是 HTTP 状态码正常、`code` 非 200 的失败很容易被漏掉。

### 2.2 端点表

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `auth/sign-in` | 登录（返回令牌） |
| GET | `comics/{id}` | 作品详情（响应为 `data.comic`，单数） |
| GET | `comics/{id}/eps?page=N` | 章节（episode）列表 |
| GET | `comics/{id}/order/{order}/pages?page=N` | 某章节的图片列表（**用章节序号 `order`，不是章节 id**） |
| GET | `comics/search?page=N&q=<编码后>` | 搜索 |
| GET | `users/profile`、`users/{id}/profile` | 个人资料 |
| GET | `users/favourite?page=N` | 收藏 |
| POST | `users/punch-in` | 签到 |

两点值得单独写出来：

- 章节图片列表用的是 **`order`（章节序号）**，不是章节 id。这个字段名看着像可互换，实际不是；传 id 拿不到页列表。
- **详情里 `comic` 是单数**。分页外壳的列表字段是复数，详情不是，按同一套字段名去读会取空。

首页/推荐与历史记录：私有存档的 6 篇文档加两个公开参照实现里**都没有这两个端点**。
所以这两个方法直接返回 `Unsupported`，而不是造一个看起来合理的地址。
宁可功能缺失并明确报"未支持"，也不要留一个永远 404 的接口。

### 2.3 请求头清单

| 请求头 | 说明 |
| --- | --- |
| `api-key` | 客户端 api-key（取值不写入本文） |
| `accept` | — |
| `app-platform` | 平台标识 |
| `app-version` | 应用版本 |
| `app-build-version` | 应为 **45**（原先用 44，见 2.8） |
| `app-uuid` | 用固定值 `defaultUuid`，不是每台设备随机生成 |
| `app-channel` | 渠道 |
| `image-quality` | 三档画质（见 2.7） |
| `time` | 时间戳，需叠加 `Server-Time` 偏移（见 2.6） |
| `nonce` | **固定常量**，不是每请求随机（见 2.8） |
| `signature` | 五段签名结果（见 2.4） |
| `authorization` | 登录后添加 |
| `app-nonce` | 只有参照实现会发，完整客户端不发；实测发了不报错，目前保留 |
| `Content-Type` | **所有请求都带**，不只是 POST |

### 2.4 签名：五段，不是八段

```text
msg  = lower( path + time + nonce + httpMethod + apiKey )      # 5 段
sign = hex( HmacSHA256( key, msg ) )                           # 小写十六进制，64 字符
```

注意三点：

1. 拼接结果**整体转小写**之后再算 HMAC；
2. `httpMethod` 是 `get` / `post` 这种小写形式；
3. 输出是**小写**十六进制的 64 字符，大写会被判失败。

**两份存档文档曾经冲突**，这是本项目里代价最大的一次"以文档为准"：

| 来源 | 说法 |
| --- | --- |
| 存档 `02-api-protocol.md`（API 层） | 8 段，含 `baseUrl`、`appVersion`、`buildVersion` |
| 原生层分析 | 5 段，**明确注明不含那三项** |
| 存档里的一处签名示例原文 | 结构正是 `path + time + nonce + httpMethod + apiKey`，整体小写 |
| 采用 | **以原生层与示例为准（5 段）** |

我按 8 段实现过一版，改回 5 段之后才走通。教训：**文档层级不等于可信度层级**，离代码越近的记录越该优先。

### 2.5 密钥从哪来，以及为什么第三方复现不了

签名密钥来自原生库的 `getStringSigFromNative()`，返回 **63 字节 ASCII**。

关键在于：原客户端会**校验 APK 自身的签名**，签名对得上才返回正确密钥。
第三方重新打包的 APK 签名不同，拿不到那份正确值——**这个派生过程无法复现**，只能使用客户端里已经存在的那份常量。

也正因如此，凭据管理在本项目里改过两次：

| 阶段 | 做法 |
| --- | --- |
| 最初 | 内置密钥 |
| 开源脱敏 | 运行时提供：环境变量 `TRICOMIX_PICA_APIKEY=…` / `TRICOMIX_PICA_SIGNINGKEY=…`，或本地文件 `~/.tricomix/pica-keys.properties`（`apiKey=` / `signingKey=`）；仓库不含任何密钥 |
| 现状（所有者决定） | 重新内置常量，同时保留环境变量/本地文件覆盖，便于调试与将来换密钥 |

缺失凭据时的行为是**明确报错并指出该设哪个环境变量**，不静默用错值——静默的后果是表现为"签名一直被拒"，极难排查。

一条必须留档的风险：该密钥**曾被推送过**。强制推送后它已不在可达历史中，但托管方可能在一段时间内保留未被引用的对象，因此稳妥的判断是**它应视为已暴露**。它不是本项目能轮换的东西（属于对方客户端），只能作为已知事实记录。仓库公开意味着任何人都能拿到这两个值。

还有一处工程细节值得单列：该密钥含 3 个需要转义的特殊字符（反斜杠、双引号、美元符）。第一次直接拼进 Kotlin 字面量时编译报 `Unsupported escape sequence`。写回这类值必须先转义——`\` 变成 `\\`、`"` 变成 `\"`、`$` 变成 `\$`——否则字符串会被截断或解析错。

### 2.6 Server-Time 时间同步

服务端在响应头返回 `Server-Time`。客户端把它与本地时间的**差值持久化**，后续请求的 `time` 字段加上该偏移。

这一步不是可选项：签名里有 `time`，客户端时钟一漂移，签名就整体失效，而失败现象看起来像"密钥错了"。
把偏移存下来，比每次请求前校准一次更省，也更能容忍容器/手机上的时钟抖动。

### 2.7 图片质量三档，以及 HIGH 为什么映射到 normal

PicACG 只有三档画质，且通过 **`image-quality` 请求头**下发，**不是 URL 参数**：

| core 档位 | PicACG 取值 | 说明 |
| --- | --- | --- |
| LOW | `low` | — |
| MEDIUM | `normal` | — |
| HIGH | `normal` | **不**升级为原图：原图通常大得多，用户选 HIGH 不代表要原图 |
| ORIGINAL | `original` | 只在这一档取原图 |

core 有四档而服务端只有三档，必然有一个档位要合并。把 HIGH 合并进 `normal` 而不是 `original` 是刻意的：
否则"高画质"会悄悄变成"每次都下载几十倍体积的原图"。

### 2.8 三处差异：都曾导致 401 与代码 1005

现象都一样——请求被拒——但根因是三件不相关的事，这就是私有 API 最难受的地方：**错误码不区分原因**。

| 项 | 错误做法 | 正确做法 |
| --- | --- | --- |
| `nonce` | 每请求随机生成 | **固定常量** |
| `User-Agent` | 完全不发 | 必须发 `okhttp/3.8.1` |
| `app-build-version` | 44 | **45** |
| `app-uuid` | 动态生成 | 固定值 `defaultUuid` |
| `Content-Type` | 只在 POST 带 | **所有请求都带** |

另外逐字核对过：`api-key` 与 HMAC 密钥和完整客户端**完全一致**。
也就是说这三处修好之前，密钥一直是对的——失败与密钥无关，纯粹是请求形态不对。

值得记下的是 `nonce` 这条：按常识，nonce 就该每次随机；但这里服务端参与签名的 nonce 是**客户端固定常量**，改成随机会让签名与请求头对不上。

| 真机 | 已验证 | 使用者实测"哔咔全正常" |
| 首页/推荐、历史 | **不实现** | 任何可得资料里都没有端点 |
| 会话跨重启 | 不支持 | 令牌只在运行内存 |

## 三、两条链路放在一起看

同属"内容源"，坑的位置完全相反：

| 维度 | EH（网页站） | PicACG（私有 API） |
| --- | --- | --- |
| 失败表现 | 解析出 0 条，不报错 | HTTP 正常但 `code` 非 200 |
| 主要风险 | 站点改版，选择器失效 | 请求头或签名形态不对 |
| 身份机制 | cookie，无 token | 令牌 + 每请求签名 |
| 时效性 | 选择器与路径会变（`gtoken` 就是例子） | 端点稳定，校验严格 |
| 最贵的一次错 | 按单元格取值，封面与作者取不到 | 按 8 段签名实现，一直 401 |
| 现在的对策 | 抓真实页面钉选择器，及时删掉失效解析器 | 以原生层与示例为准，写清每一条差异 |

还有一条通用规矩：**接口层不编造能力**。
EH 的历史是客户端本地记录，服务端没有对应端点；PicACG 的首页/推荐在任何可得资料里都不存在。
这类方法一律返回 `Unsupported`，由上层决定怎么补——比返回一个看起来能用的空列表诚实得多。

## 四、几条结论

1. **合成样本只能证明"逻辑自洽"，不能证明"真实长这样"。** 项目里 168 个单测（JM 56 / Pica 40 / EH 72）全部用自写样本，另有 12 项不联网自检。真实页面形状必须靠真实响应核对——EH 的封面与作者就是这么修出来的。
2. **文档冲突时，选离代码最近的那份。** 8 段与 5 段的冲突，最终由原生层分析与存档里的签名示例定案。
3. **静默失败的地方要额外加探针。** `hath` 的误报就是探针自己写错了匹配串，而不是数据缺失。
4. **失效的实现路径要删干净。** 留着一份不再工作的 `gtoken` 解析器，会让人误以为还有第二条路。
5. **区分"协议错"与"网络不可达"。** 早期多次把容器网络超时误判为协议问题，正确做法是先看是超时（HTTP 000）还是服务端返回了错误码，再下结论。
6. **不改"未验证"，也不把"请求到达了服务端"写成"验证通过"。** 这份账本里 EH 的登录与收藏至今仍标着未实测，尽管它们的单测是绿的。
