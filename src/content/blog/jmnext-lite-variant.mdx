JMNeXt 在 1.8.0 加了一个 `lite` 变体，面向极低性能设备。
它不是另开一个仓库、也不是拉一条分支，而是**同一个应用的两档裁剪**：
同一套代码、同一个分支，编译出两个包。

这篇文章记录三件事：裁剪线画在哪、怎么让两份产物在系统里互不干扰、以及**怎么用数字证明
lite 确实更轻**——最后一条里有一个负面结论，我原以为它会是正面的。

> 源码与构建配置都在 [moyingyilang/JMNeXt](https://github.com/moyingyilang/JMNeXt)。
> 关于这个项目构建提速的部分，另见 [/blog/issue-fix-and-build-speed-lessons](/blog/issue-fix-and-build-speed-lessons)。

## 一、为什么是 product flavor，不是 git 分支

两条路的代价对照：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| git 分支 | 拉一条 `lite` 分支独立演进 | 两个代码库：每个 bug 修两遍、功能会漂移、每次改动都要 cherry-pick |
| **product flavor** | 同一套代码出 `full` / `lite`，开关是编译期常量 | 代码里维护一套开关，但配 R8 后关掉的分支会连代码一起被删 |

选 flavor 的核心理由不是"省事"，而是**lite 不是另一款应用**。
分支的必然结果是两者越走越远：主线的新修复不会自动流到 lite，
而低端设备上的用户恰恰最需要修复。

形态定下来之后，机制上只有两条硬要求：

1. **开关必须是编译期常量**，不能是运行时开关。`BuildConfig.LITE` 是 flavor 提供的编译期常量，
   `if (!BuildConfig.LITE)` 包住的整段代码与资源会被 R8 一起删掉，而不是"编进去但不执行"。
2. **判断集中在一个门面里**。所有"lite 要裁剪什么"都收进 `LiteFeatures`，
   而不是把 `if (BuildConfig.LITE)` 散落到几十处——散落的开关迟早漏一个，
   漏掉的那一处会以"lite 上有个功能不能用"或"看起来还是卡"的形式出现，很难归因。

主题层的处理尤其如此：lite 下 `Styles.of` 编译期早退到纯色方案，另外三种玻璃风格的规格定义整段消失。
**不在调用点写 if**，否则要改几十处，而且以后每加一个卡片都要记得再写一次。

## 二、裁剪线画在哪

划线标准是一句话：**砍掉「玻璃材质之上的附加复杂度」，保留"没有它就不是阅读器"的部分。**

### 砍掉的

| 砍掉项 | 理由 | 连带处理 |
| --- | --- | --- |
| 玻璃 / 模糊 / 通透模式与其余主题风格 | 每帧模糊是这台设备最可能的卡顿源 | 界面风格只留 Miuix 与 Material 两种纯色；`GlassSurface` 退化为普通 Surface |
| 壁纸（拉取 + 常驻模糊） | 一个网络功能加一张常驻模糊的大图 | 背景固定纯色；`LocalWallpaper` 给空状态 |
| 莫奈 / 动态取色 | 需要系统取色管线 | 固定主色 |
| 悬浮底栏 | 玻璃材质之上的附加复杂度 | 用普通底栏 |
| 预测性返回 | 动画的一部分 | 交给系统默认返回 |
| 动效性格、共享元素、条目进出场 | 低端机上动画是最直观的"卡" | 交互仍有即时反馈，只是不做过渡 |
| 评论、作者页、书库页 | 非阅读必需 | 入口一并隐藏 |
| 签到、通知（含 12 小时闹钟）、随机按钮 | 附带网络与后台成本 | 设置里对应项一并隐藏 |
| 周刊 | 同上 | — |

注意壁纸那一行的连带效果：壁纸一关，依赖它的磨砂与颗粒**自然全部消失**——
它们的物理前提就是"背后有东西"。这比逐个去关模糊开关干净。

### 保留的

首页分区浏览 / 分类 / 搜索、阅读器（翻页、预取、进度记忆）、收藏 / 历史 / 追更、
下载、标签屏蔽、登录，以及设置里的必要项（阅读偏好、存储、关于）。

两处取舍值得单独说：

- **下载保留**。它是另一个大模块（存储、任务管理），是最能减重的一块；
  但低性能设备往往网络也差，离线阅读更必要。
- **标签屏蔽保留**。它会在后台逐条读详情取标签，对低性能加差网络是持续成本；
  但砍掉等于**破坏用户已有的屏蔽设置**。用户数据优先。

### 时间换性能的几项

| 取舍 | lite | full |
| --- | --- | --- |
| 图片淡入 | 关（每张图少一次合成与重绘） | 开 |
| 条目进出场动画 | 关（关掉的是每一帧的重排与重绘） | 开 |
| 阅读器预取窗口 | 前 1 / 后 3 | 前 2 / 后 8 |

预取窗口收窄的逻辑是**内存换流量**：每张漫画图解码后都是几 MB 级别，
低端设备上内存比流量紧张，少预取几页就是直接的内存收益。

## 三、两份产物怎么在系统里共存

lite 的 `applicationId` 与 full 不同（lite 带 `.lite` 后缀，即 `com.jmnext` 与 `com.jmnext.lite`），
所以**两个包可以同时安装、互不覆盖**，用户想两个都留着也行。
代价是数据不共享：lite 与 full 各自的收藏与设置互相独立。这是刻意的——
共用一个包名就不可能让两者并存。

`versionName` 的四个变体分开标记，取值为后缀形式 `.debug`、`.lite`、`.litedebug`：

| 变体 | 后缀 |
| --- | --- |
| full / release | 无 |
| full / debug | `.debug` |
| lite / release | `.lite` |
| lite / debug | `.litedebug` |

这里有一个 AGP 的坑：**不能**用 flavor 的 `versionNameSuffix` 与 buildType 的 `versionNameSuffix` 去拼。
AGP 会把两段后缀都接上，得到 `x.y.z.lite.debug`，而要求是一个连写标记 `litedebug`。
所以改成在 `androidComponents.onVariants` 里按变体整体设置。

应用名则走**flavor 专属资源覆盖**：`app/src/lite/res/values/strings.xml` 里覆盖 `app_name`。
这不需要打开项目的 `resValues` 构建特性——资源覆盖是另一条路径，不用为了改一个字符串去开它。

## 四、四项量化验收指标

实现前后各测一次，同一台机器。数字如下（APK 压缩后两边都是 3136 KB）：

| 指标 | 怎么测 | full | lite | 结论 |
| --- | --- | --- | --- | --- |
| dex 体积 | 本地解析 APK 分类 | 3845 KB | 3844 KB | 几乎不变 |
| 冷启动 `TotalTime` | `am start -W` | 240 ms | 208 ms | 降约 13% |
| PSS 内存 | `dumpsys meminfo` 取 Total PSS | 74,959 KB | 70,322 KB | 降约 6% |
| 滑动卡顿帧 | `dumpsys gfxinfo` 的 janky frames | 29.96%（444/1482） | 20.38%（249/1222） | 相对降 32% |

**第一行是这一版最重要的负面结论：削功能换不来体积。**
dex 只差 1 KB——因为体积被**依赖**占满（Compose + Material3 + Coil + OkHttp + kotlinx），
不是被应用自己的功能代码占满。

那 1 KB 的来处很明确：`Styles.of` 的编译期早退让另外三种玻璃风格的规格定义被 R8 整段删除。
**机制是对的，只是这一层的体量本来就小。** 所以 lite 的价值必须用运行时指标证明，
不能拿体积当卖点——除非动依赖，而依赖是功能的地基。

第四行的 `gfxinfo` 是这套验收里最有用的一项。前几版我能测启动、测不了流畅度，
只能含糊说"感觉还行"；`gfxinfo` 直接给出**客观的卡顿帧比例**，不用靠感觉。

## 五、测量方法：预热 + 换顺序

这四项里，冷启动与 PSS 是**前后对比型**指标，对测量顺序非常敏感。
我第一次测量的结果是这样的（lite 先测、full 后测，都是装完包直接测）：

| | 冷启动 | PSS |
| --- | --- | --- |
| lite | 289 ms | 103,561 KB |
| full | 252 ms | 75,538 KB |

**结论完全相反**：lite 看起来更慢，还多占约 28 MB。
原因是**被测顺序**——第一个被测的应用承担了 JIT、类加载与页缓存的冷启动成本，
而这些成本与功能多少无关。

预热一轮并换顺序（full 先、lite 后）之后，才得到第四节那张表里的数字。

> 教训：性能类的前后对比，至少要"先各预热一次 + 换顺序复测"。
> 只测一轮并且固定顺序，很容易把方向完全相反的结论写进发布说明。

## 六、一处更正：注释里的 52% 与正文的 32%

第四节最后一行有一个记录在案的更正。

我在 CHANGELOG 的注释里曾把卡顿帧的相对降幅写成 **52%**。
它的正文数字是 32%——按原始计数，29.96% 降到 20.38%，相对降幅约 32%。
52% 是把两个比例相减时算错了口径。

- 正文数字以 **32%** 为准；
- 那条 52% 的注释已改掉；
- 我把这次更正留在记录里，而不是悄悄改掉：**当同一份材料里注释与正文并存时，
  两者都可能被后续引用**。52% 这种"看起来更漂亮的数字"如果没人核对，
  很容易被抄进发布说明，而它与原始计数对不上。

这类错误与数字本身一样值得记档：错的是一个数字，暴露的是"注释没有跟正文一起核对"。

## 七、测试与编译验证

单测是分变体跑的：

| 变体 | 结果 |
| --- | --- |
| full | 155 通过 |
| lite | 132 通过 + 19 跳过 |

跳过的 19 个是"完整风格表"断言——lite 有意折叠了那张表，测试用 `assume` 跳过并写明原因，
而不是删掉：full 仍靠它们守护风格表。

编译验证还有一个容易踩的坑：`app` 现在有两个 flavor，**任务名必须写全**：

```bash
gradle :app:compileFullDebugKotlin :app:compileLiteDebugKotlin
```

写成 `:app:compileDebugKotlin` 会直接报 `Ambiguous matches`。
我第一次写成简写，看到报错先记成了"编译失败"——其实那一次**根本没有开始编译 Kotlin**，
是任务没解析出来。这两件事在记录里必须分开。

## 八、明确未验证的部分

上面四项指标覆盖的是体积、启动、内存与帧统计。**它们都是可测量的中间量，
不等于真实观感。** 以下部分我没有验证，写清楚，不含糊带过：

- **lite 的真实手感**：翻页、滚动的"顺不顺"要人在真机上长期用才能判断，
  `gfxinfo` 的卡顿比例只是它的一个代理指标；
- **lite 在主机上的运行情况**：这一版只在虚拟机上装了 lite，
  另一台机器上装的是 full。也就是说"两个包同时装在一台机器上互不干扰"这一点，
  配置上成立，但没有在真机上走一遍；
- **关态开关的描边视觉效果**：lite 的实心风格下，Material3 默认的关态轨道色与卡片底色太接近，
  用户看不出轨道在哪，所以加了显式描边。描边本身是按设计做的，
  但它在真机上的观感没有确认。

## 结语

把这次的结论压成几条可复用的：

1. **裁剪用 flavor，不用分支**：同一款应用的裁剪版，必须能自动拿到主线的修复；
2. **开关放编译期、判断收进一个门面**，否则迟早漏一处；
3. **先量后改，并且给测量加上"预热 + 换顺序"**，否则可能得到方向相反的结论；
4. **负面结论要留在记录里**——"削功能换不来体积"比任何正面数字都更能约束后续决策；
5. **注释与正文要一起核对**，同一个数字写了两遍就有两个版本。
