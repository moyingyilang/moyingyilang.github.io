阅读器的预取深度是个典型的"没有全局最优"的参数：翻页快的人希望往前多取几页，
慢慢看的人在浪费带宽。手册上写一个 6，只是取了个中间值。

我想做的是让它在用户自己的设备上把这件事试出来 —— 不联网、不上传、不引入 ML 运行时，
几百行 Kotlin，行为可解释、可关闭、可回退。仓库在 [JMNeXt](https://github.com/moyingyilang/JMNeXt)。

这篇文章按顺序回答四个问题：调什么、看什么、怎么判好坏、怎么证明它没乱调。

## 一、先写死原则

设计阶段先把这些定死，避免实现时跑偏：

| 原则 | 具体约束 |
| --- | --- |
| 纯 Kotlin、零新依赖 | 算法本体目标数百行以内；不用 ONNX / TensorFlow / DJL |
| 全部本地 | 不采集、不上传；学习结果只写本机配置 |
| 只在可观测范围内调 | 不猜喜好；每个参数人都能读懂、日志能解释 |
| 不许变坏 | 硬边界 + 守擂者/挑战者；失败率上升立刻回退默认 |
| 可关闭 | 关闭后行为与现在完全一致 |
| 先量后改 | 每步决策都能在日志里看到窗口、适应度、θ 变化、是否采纳 |

## 二、调什么：四个参数，各自带硬边界

| 参数 | 默认值 | 范围 | 为什么是它 |
| --- | --- | --- | --- |
| `prefetchDepth` | 6 | 2 至 12 | 预取提前量。翻页快的人受益，慢慢看的人浪费带宽 |
| `prefetchConcurrency` | 1 | 1 至 3 | 预取并发。串行保证近处优先；并发提高吞吐但挤占带宽 |
| `cacheBudgetMB` | 256 | 64 至 512 | 图片缓存上限。内存紧的设备应调小 |
| `retryBackoffMs` | 800 | 200 至 3000 | 下载失败后的退避。网络差的人需要更宽容 |

四条都有明确的硬边界。算法只能在区间内移动，越界一律夹回。
另外有一条底线：**任何影响正确性的参数都不纳入** —— 反切片公式、页码映射、缓存淘汰语义都不碰。

第二阶段（需要更多观测才敢纳入）列了解码目标尺寸、横向模式预渲染页数、章节预取开关。
其中解码目标尺寸与此前测得的数据相关（解码只占 86ms、下载占 1078ms），
若调小没有收益就不纳入。

在实现里，一个参数就是名字、范围、默认值三项，构造时用 `require` 校验
"范围合法"且"默认值落在范围内"。

## 三、看什么：信号全部来自本机既有日志与计数

| 信号 | 来源 | 用途 |
| --- | --- | --- |
| 单页呈现耗时 | 反切片总耗时、下载耗时、"预取第 N 页"日志 | 适应度的延迟项 |
| 缓存命中 | 分界后"反切片是否紧跟下载行"的配对 | 适应度的命中率项 |
| 每页下载字节 | `[反切片] 下载 …B` | 适应度的带宽项 |
| 失败与取消次数 | 下载异常、取消守卫、加载失败行 | 安全项（越界即回退） |
| 停留时长、翻页方向、翻页间隔 | 阅读页新增的轻量打点（仅计数与耗时） | 习惯项：区分"快翻"与"慢读" |

习惯项的判据是明确的、可解释的：以本次会话的**中位停留时长**为分界，
快翻用户（中位停留小于约 1 秒）加权延迟项，慢读用户加权带宽项。
这就是"适配不同使用习惯"的具体含义，不是玄学。

观测的原子单位是一次翻页，只采计数与耗时、不采内容，字段有五个：
该页呈现耗时、该页下载字节（命中缓存为 0）、是否命中缓存、是否失败、
以及用户在该页停留多久。取消不算失败，单独计数 —— 它既不是失败也不是命中。

有一个容易出错的细节：Android 用 Coil 显示图片，它公开的 `SuccessResult` 与
`EventListener` 都拿不到下载字节数（`FetchResult` 是空标记接口）。
所以"字节未知"必须是一个独立状态，而不是 0：

- 全部样本都未知时，适应度**把带宽这一项的权重整个丢掉**，只用延迟、未命中、失败来比较；
- 若把未知当成 0，这一端会显得"无限省流量"从而支配评分。

为此专门写了 4 个单测，证明"未知"与"零字节"在评分上的区别是设计好的、不是碰巧。

## 四、怎么判好坏：一个小数，越小越好

```
cost = wL * 归一化单页呈现耗时中位数
     + wB * 归一化每页下载字节
     + wM * 未命中率
     + wF * 失败/取消率
```

权重由习惯档决定，`wF` 固定为惩罚项且权重最高：

| 习惯档 | 判据（中位停留） | wL 延迟 | wB 带宽 | wM 未命中 | wF 失败 |
| --- | --- | --- | --- | --- | --- |
| QUICK | 小于 1000ms | 1.0 | 0.2 | 0.5 | 3.0 |
| NEUTRAL | 1000 至 3000ms | 0.6 | 0.6 | 0.4 | 3.0 |
| SLOW | 大于 3000ms | 0.3 | 1.0 | 0.3 | 3.0 |

为什么这样定：

- 快翻的人在等图，延迟就是他的全部体验，带宽浪费他感觉不到；
- 慢读的人图早就下完了，延迟已经饱和，预取太深只是白下很多页；
- 失败权重最高，因为任何配置下"出错"都不能被延迟或带宽的优势抵消，这是安全底线；
- 所有项都按"当前会话内可比的量"归一化（延迟除以 1000ms、每页字节除以 1MB，
  并分别在 5.0 与 10.0 处截断），避免换了个网络环境就不可比。

权重数值本身是**设计选择，不是实测结论**。它正确与否由离线回放检验：
如果回放里快翻轨迹没有把深度调大，先改的就是这里。

空窗口返回 NaN，明确表示"本窗口不参与评估"，而不是当成 0 分最优。

## 五、算法形式：对角高斯 NES

核心是一个极小的自然进化策略，只负责"搜索分布、采样、更新"，不涉及任何业务参数与日志。
适应度**越小越好**，并且只有排名参与更新（排序适应度整形），绝对数值不参与 —— 在线场景噪声大，这样更稳。

| 环节 | 做法 |
| --- | --- |
| 搜索空间 | 参数先归一化到 [0,1]：`x = (p - lo) / (hi - lo)` |
| 搜索分布 | 对角高斯 `N(θ, σ²I)`，σ 初值 0.15，夹在 0.02 至 0.30 |
| 采样 | 每代 λ = 6 个候选，两两对偶（`θ ± σ ε`） |
| 更新 | `θ ← θ + (η / (nσ)) Σ u_k ε_k`，默认 η = 0.02、不衰减 |
| 排序整形 | u 从最好者 +0.5 到最差者 -0.5，无梯度 |
| 步长自适应 | 本代最好者优于历史最好则 σ 乘 1.05，否则乘 0.95，两端夹住 |
| 越界处理 | 按镜像折回（而不是夹住） |
| 可复现 | 固定种子，相同种子结果完全可复现 |

**在线约束决定了"一代"的形状**。一个窗口只能评估一个配置 ——
没法对同一段真实使用做反事实评估。所以一代 = 1 + λ 个窗口：

1. 第 0 个窗口评估**现任参数**，作为本代比较基准（避免跨时段噪声导致误采纳）；
2. 之后 λ 个窗口各评估一个采样候选；
3. 一代结束时用这 λ 个候选的适应度更新搜索分布。

窗口大小默认 20 次翻页（或会话结束时结算），**窗口内只用一个参数向量**，
窗口边界的日志统计就是该向量的适应度，窗口结束后才可能切换。

有几个坑是靠单测的逐代轨迹量出来的，都写在代码注释里：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 300 代后距离最优 0.31 | 用"候选是否优于均值"做 1/5 成功规则，在凸景观上恒约 0.5，步长一路放大到上限 | 判据改成"本代最好者是否优于历史最好" |
| 收敛测试里第 0 维跑反了方向 | 越界时夹住，边界处候选堆在同一点，破坏对偶采样对称性 | 改成镜像折回 |
| 更新方向被污染 | 更新中 `mean` 被改写，ε 却按新均值算 | 抽样时的均值先存一份 |
| 均值在边界乱撞、σ 缩到下限 | η 曾用 0.35，单代位移约 0.5（半个参数空间） | η 降到 0.02，单代步长约为 1.9η |

单代步长与 σ 无关这一点值得单独说：ε 是标准正态，与 σ 无关，
所以 `θ ← θ + (η/(nσ))·Σ u_k ε_k` 的单代位移约 1.9η。按直觉调大 η 会直接毁掉搜索。

还有一个设计选择：应用实际使用的**不是带抖动的均值 θ，而是 elite** ——
取得过最好适应度的那组参数。恒定学习率下均值会在最优点附近持续随机游走
（单测轨迹里 gen=11 时距离最优 0.013，gen=60 又漂到 0.205），而 elite 始终是"找到过的最好那组"。

## 六、安全阀与边界

"不许变坏"是靠机制兜住的，不是靠参数调得稳：

| 机制 | 具体规则 |
| --- | --- |
| 硬边界 | 归一化空间夹在 [0,1]；mean 更新后也夹；业务值再按 lo/hi 夹一次，整数参数取整 |
| 冷启动 | 初始 θ = 当前手工调好的默认值（预取 6、并发 1、缓存 256MB），装上或升级后行为与现在完全一致 |
| 关闭开关 | 关闭时 `params()` 永远返回默认值，行为与现在完全一致 |
| 守擂者/挑战者 | 始终保留当前生效配置；挑战者要**明显更优**才被采纳 —— 代价需低于基准 (1 - 0.05)，即 5% 的采纳余量 |
| 失败即回退 | 窗口内失败与取消占比超过 25%，立刻写回默认值，并进入 3 个窗口的冷却期（只统计、不学习） |
| 空窗口 | 不参与评估，避免被当成 0 分最优 |
| 窗口中途不换参数 | 避免同一页行为不一致 |

窗口结算的结果不是布尔值，而是一个分类型别：空窗口跳过、保持现任、采纳挑战者、回退、
冷却中、以及仅供日志的一代结束。分开表达是为了日志和测试能区分清楚。

状态存在应用数据目录下的 `selftune.json`，含 schemaVersion、θ、σ、incumbent、窗口计数、
冷却计数、冷启动标记与时间戳。容错规则很硬：解析失败、schema 不认识的版本、
维度看起来不对、σ 非有限或非正 —— 一律返回 null，由调用方回到默认值，
**绝不带着半截状态运行**。

这里也有两个被单测抓出来的真实缺陷：历史最好适应度初值是正无穷，
而 JSON 不允许无穷大，于是"第一次保存必然抛异常、学习状态从来没落盘过"，
改成用 `null` 表示"还没有"；以及早期保存路径把异常吞掉，
导致保存一直没成功而日志里一点痕迹都没有。现在两条失败路径都会说话：
没有配置存储、以及写入失败，各自打一条日志。

## 七、判据与验证：三层证据

### 第一层：算法本体单测，7 个

合成带噪声的二次目标，固定随机种子，断言在若干代内收敛到最优附近（带容差），
并且相同种子结果可复现。覆盖平稳目标收敛、在线场景漂移有界、步长按成功比例收缩放大并被两端夹住、
更新方向朝适应度更好的候选、均值始终留在归一化范围内。另有一个诊断用例打印后验轨迹，用来量位移。

### 第二层：调参器与序列化单测，22 个

| 类别 | 数量 | 覆盖内容 |
| --- | --- | --- |
| 调参器 | 18 | 参数越界夹回、习惯档判定与权重方向、空窗口不评估、挑战者没赢不采纳、明显更好才采纳、失败率超限回退并冷却、损坏状态回默认、窗口中途参数不变、状态可保存可恢复 |
| 字节未知 | 4 | 字节全未知时排序完全由延迟决定、未知与零字节在单窗口代价上等价、已知字节仍按真值计、已知条数为零时不依赖字节项 |

两边合计 29 个单测。另有 Android 侧采样器的 5 个单测（报告 tests=5 failures=0）。

### 第三层：离线回放，这是能不能上线的闸

数据来源必须分清：

| 类型 | 内容 |
| --- | --- |
| 真实 | `shared/src/test/resources/selftune-trace.csv`，从真机日志抽出的 177 条反切片下载样本（字节数, 下载毫秒），取自同一连续时段。字节中位数 898KB、下载中位数 836ms、范围 221 至 4170ms |
| 构造 | 停留时长。日志里几乎没有停留记录（只有 16 行键盘翻页），所以构造了四种场景：150ms 狂点、400ms、1000ms、4000ms 慢读 |

模型刻意保持简单、可解释：页面最多提前 d 页开始下载，
可用提前时间 = `min(d, 当前页序号) × 每页停留`；需要时间 = 下载毫秒 / 并发数；
够则命中（延迟约 0），不够则延迟 = 缺口 + 完整下载时间；
结尾处被预取但没看到的 d 页字节按页均摊计入浪费。

深度扫描（中位延迟 / 150 页中的命中数）：

| 停留 | d=2 | d=3 | d=4 | d=6 | d=9 | d=12 |
| --- | --- | --- | --- | --- | --- | --- |
| 150ms | 1896ms / 5 | 1709ms / 28 | 1535ms / 46 | 1231ms / 72 | 790ms / 113 | 565ms / 128 |
| 400ms | 1341ms / 60 | 911ms / 100 | 643ms / 120 | 383ms / 134 | 207ms / 141 | 147ms / 143 |
| 1000ms | 453ms / 131 | 180ms / 142 | 49ms / 147 | 20ms / 148 | 20ms / 148 | 20ms / 148 |
| 4000ms | 12ms / 149 | 12ms / 149 | 12ms / 149 | 12ms / 149 | 12ms / 149 | 12ms / 149 |

浪费（页均摊）随深度近似线性：d=2 约 15KB/页，d=12 约 79KB/页。

回放的判据只有一条，写死在测试里：**狂点场景最终选出的预取深度不小于慢读场景**。

- 狂点（150ms/页）：深度 **7**、并发 2、缓存 374MB、退避 572ms；
- 慢读（4000ms/页）：深度 **3**、并发 1、缓存 89MB、退避 1680ms。

断言 `7 >= 3` 通过。

这张表说明了两件事：

1. **方向正确**。翻得越快，延迟项越重要，算法把深度调大；翻得慢时延迟项已经饱和
   （d=2 就命中 149/150），再加深度只是多下载，于是算法把深度收小。
2. **常见阅读速度下最优深度并不大**。1000ms/页时 d=6 已经到 20ms 延迟、命中 148/150，
   再深没有收益。这也解释了此前"预取提前 6 页仍未见中位数下降"的实测 ——
   瓶颈不在深度，而在单页下载本身。

## 八、两端接线：参数侧与反馈侧各自接什么

算法核心放在 `shared`，Android 经 `:shared` 使用，桌面端用
`kotlin.srcDir("../shared/src/main/kotlin")` 直接编译同一份源码，所以两端共用一份实现。

| 端 | 参数侧（读） | 反馈侧（写） |
| --- | --- | --- |
| 共享层 | `SelfTune.params()`，未启用时返回默认值 | 每次翻页结束调 `onPage(PageSample(...))`；取消单独走 `onCancellation()` |
| 桌面端 | 阅读页预取深度不再是硬编码 6，改为读 `SelfTuner.prefetchDepth`，并把本窗口实际深度写进日志 | 进页记时、离页结算，喂回五个字段；字节由 `RemoteImage` 的带尺寸加载变体暴露真实值 |
| Android 端 | 预取窗口 `PREFETCH_BEFORE/AFTER` 改为按比例缩放（`(base*depth+3)/6`），默认深度 6 时系数为 1、窗口与今天逐位相同 | 页级 `State.Success` 处记延迟、命中、字节；屏幕级在当前页变化时结算停留并喂样本；换话清空 |

Android 的采样器是独立的，5 个单测通过。状态落 SharedPreferences（`jm_selftune`），
未初始化时返回默认值；桌面端落 Preferences，默认开启。

有一个旋钮两端都没有对应物：`prefetchConcurrency`。桌面阅读页的预取是**串行**的
（并发会让更靠后的页先到，反而没用），Android 侧没有并发上限。
所以这一个**主动不接** —— 不为了"用满四个旋钮"给它造一个假落点。

接线过程中还有一条纪律值得记下来：Android 的图片组件是**按页实例化**的，
组件存活时间不等于用户停留时间（分页模式下相邻页也会被组合，滚动模式下页面会被回收）。
所以停留时长必须在屏幕级测。若用页级组件的存活时长当停留，
适应度依据的中位停留会被污染，习惯档判断就错了 ——
而"快翻加深预取、慢读减小"正是整个算法的立论基础，污染它比不接更糟。

同理，如果某个字段暂时拿不到真值，**宁可先不上反馈**，也不要用 0 或猜的值填进去。
用假值喂样本会让算法拿错信号去学，比不学更糟。`bytes` 的"未知"语义就是为这条纪律加的。

## 九、明确未验证的部分

必须写清楚：**接线后的真实手感只能靠真机**。

- 算法本体与调参器的证据是单测通过；接线的证据只到"编译通过 + 参数被读取 + 样本被记录"；
- 离线回放的限制不得省略：停留是构造数据、模型是简化模型、177 条样本只代表一段网络状况。
  所以回放只能证明**方向**与**量级**，不能当作真机收益的证明；
- 回放里只有 150ms 狂点与 4000ms 慢读两个场景给出了最终选出的参数；
  中间两种停留（400ms、1000ms）只在深度扫描表里；
- "算法是否真的让翻页更快、带宽更省"没有真机结论；
- 计划让日志输出每个窗口的 θ、适应度与是否采纳，据此检查有没有抖动、有没有越过安全边界。
  这一步还没有真机数据；
- Android 端字节数取自 Coil 落盘文件的真实大小，拿不到时为"未知"，这条路径只在编译层面成立；
- 权重数值是设计选择，正确性只由回放的方向判据背书，不是实测调出来的最优值。

按计划，先只记录不生效地跑一段（P1），拿到"它的建议是否合理"的证据，
再打开生效（P2），符合"先量后改"，也避免一上来就悄悄改变用户体验却无法解释。

我不打算把"学习结果"当成已验证效果 —— 效果仍然要用日志指标说话。
