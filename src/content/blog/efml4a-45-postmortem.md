## 45.1 我【做对了】什么（有证据）

### 45.1.1 基础设施：三次修正都是对的，且都被后续验证

| 修正 | 原始错误 | 验证方式 |

### 45.1.2 ★ 有限重装（本阶段最有价值的修正）

```
现像：hook 装上但 0 次调用
错误归因：函数冷门（错了 5 次方向）
正确归因：游戏有反篡改，会还原 .text
  证据：无看门狗 a8 6e 1a 39…（原始）
        有看门狗 50 00 00 58 00 02 1f d6…（活着）
最关键的一步：把「每 200ms 永远重装」改成「只在启动 8 秒内重装」
  证据：改完后 81 次调用零崩溃（两次独立复现）
  反面证据：永远重装时，连【纯只读】都崩（tombstone_04）
⇒ 这是本阶段唯一一个「一次改对、且经得起复现」的机制
```

### 45.1.3 手写 ELF `.dynsym` 解析器

```
libunity.so 是 stripped（347 个 dynsym 全是 Android API）⇒ 无法按名 hook
但 vulkan.adreno.so 有 742 个导出符号
⇒ 手写解析器成功定位 vkCmdCopyBufferToImage +0x172770
   地址验证：0x76aa276000 + 0x172770 = 0x76aa3e8770 ✓ 与符号表一致
```

### 45.1.4 用「只读验证」代替「猜测」

```
在 hook 里读回 host 前 8 字节 ⇒ 读到 ASCII "Rend"+"erBu"（RenderBuffer）
⇒ 证明指针链正确（VkBuffer→VkDeviceMemory→hostPtr）
这一步本身是对的，问题出在后续「写入」而不是「验证」
```

### 45.1.5 ★ 每次崩溃都保留了 tombstone 并做归因

```
9 份 tombstone 全部保留，每份都有 backtrace 指认
⇒ 这是最终能定位根因的唯一依据（尤其 #05 的 vkMapMemory+64 直接指认）
```

### 45.1.6 ★ 用「只读」推翻了「Android 版没有 512×512」的错误结论

## 45.3 我【应该怎么做】

### 45.3.1 上线前的「四查 + 三确认」

```
四查（针对 hook 目标）:
  ① 查分支：B / BL / B.cond / CBZ / CBNZ / TBZ / TBNZ
  ② 查 PAC：paciasp / pacibsp
  ③ 查 SP：前 16 字节内有 sub/add sp
  ④ 查频率：高频函数【禁用】周期性重装

三确认（针对任何写入）:
  ① 确认容量：目标 buffer/纹理 ≥ 要写的字节数
  ② 确认格式：真的匹配吗（BC7 vs RGBA8 vs BC5）
  ③ 确认作用域：这次写入发生在正确的条件下吗
```

### 45.3.2 工作节奏（我以后强制自己遵守）

```
1. 一次只改一个变量
2. 改完立刻用【只读方式】验证改动落地了
   （例：grep 确认 sed 生效、dump 确认字节变了）
3. 崩溃后先看 backtrace 的 #01/#02 帧，先分清「是游戏还是我的代码」
4. 先只读跑通，再考虑写入；写入永远最后一步
5. 任何「结论」在写进文档前，先问：有没有第二个解释？
```

### 45.3.3 具体到本任务的正确顺序（回顾）

```
❌ 我实际做的：先试写入 → 崩 → 改 → 崩 → 改 → 崩 …
✅ 应该做的：
   ① 只读：完整收集 512×512 的出现序列（已完成）
   ② 只读：确认 dstImage 的格式（hook vkGetImageMemoryRequirements 等低频函数）
   ③ 只读：确认 staging buffer 的大小（hook vkCreateBuffer，需要 post-call）
   ④ 三确认都通过后再写入，且第一次只写 1 个纹理、只写 1 次
   ⑤ 或者干脆走离线路线（零运行时风险）
```

### 45.4.5 ★ 最重要的一个信息（战略层）

