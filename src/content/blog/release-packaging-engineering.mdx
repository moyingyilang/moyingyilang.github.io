"构建成功"离"用户拿到正确的东西"之间，隔着不少细节。这篇文章记录一次小版本发布里
真实踩到的坑，都属于"代码明明改对了，产物却没生效"这一类。

## 一、版本号可能写在三个地方，而产物优先读清单

这次改动里，版本号分散在：

1. 代码里的常量（作为读不到清单时的兜底）；
2. 构建脚本里的包版本（`packageVersion` 之类）；
3. **构建产物的清单文件**（例如 jar 的 `Implementation-Version`）。

而运行时读版本的逻辑通常是"**先读清单，读不到再用常量**"。
于是只改常量的话，打出来的包依然自称旧版本。

**正确做法**：改完必须**解包核对**，而不是相信构建日志：

```bash
# Debian 包
dpkg-deb -f app.deb Package Version Architecture

# tar.gz 里的 jar 清单（要挑对应用 jar，别抓到捆绑运行时的 jar）
unzip -p app.jar META-INF/MANIFEST.MF | grep -i implementation-version

# 自解压 exe（先拆包，再看里面的 jar 与启动脚本）
7z x -oout app.exe && find out -name "*.jar" | head
```

最后一条尤其有用：它同时验证了"版本号对不对"和"启动参数有没有真的进包"。

## 二、打包脚本会清空自己的输出目录

我一度把多个打包目标都输出到同一个目录，结果产物会**互相覆盖并消失**。
原因是每个脚本开头都有类似：

```bash
rm -rf "$OUT" && mkdir -p "$OUT"
```

**做法**：每个目标一个独立目录，全部跑完后统一收集发布物（按扩展名与体积过滤，
排除中间文件）。

## 三、不要为了"干净"绕过跳过机制

打包脚本通常带"输入指纹未变则跳过"的机制。实测：同一个目标再跑一次只要 **0.044 秒**，
而完整重打要 **72 秒**。所以除非确实需要重跑，**不要加 `FORCE=1`**。

顺带一个数据：72 秒里只有约 **2 秒**是构建工具（打 fat jar），其余约 70 秒是
解压运行时 + 压缩 88MB 的安装包 —— 这部分是产物体积的必然代价，靠缓存消不掉。

## 四、发布前必须核对的四件事

1. **版本号三处一致**（源码常量 / 构建配置 / 产物清单），并解包核对；
2. **发布说明与事实一致**：我出过一次"先写了不含某平台包，后来补齐了包却只改了文末，
   正文开头还写着不含"的事故 —— 发布物、变更日志、给用户的回复三处要一起改；
3. **附件清单**：数量与命名规则要和上一版对齐（用户会按命名找包）；
4. **功能冒烟**：不要因为"只是改版本号"就跳过 —— 至少跑一次测试与一次最小启动。

## 五、签名与平台包

移动端 release 包需要签名配置（密钥库与口令通常不入库）。发布前应确认：

- 配置文件存在且键齐全；
- 产物确实**已签名**（否则很多设备装不上）；
- 版本号（`versionCode` / `versionName`）一并递增 —— 只改名字不改数字会导致"装了但没更新"。

核对方式同样是读构建实际生效的**合并清单**，而不是看构建脚本：

```bash
grep -oE 'versionName="[^"]*"|versionCode="[^"]*"' \
  build/intermediates/merged_manifest/*/AndroidManifest.xml
```

## 结语

这一节的共同主题是：**别相信"构建成功"，去核对产物。**
版本号、启动参数、签名、附件，都属于"看不见但用户立刻能发现"的东西。
