## 69.1 实验设计

**A/B 对照，唯一变量是 `.chk` 是否被修改：**

| | 状态 | 304×68 纹理是否上传 |
|---|---|---|
| **A（Round 17）** | 原始文件 | **✅ Copy #57 ext=304x68** |
| **B（Round 18）** | 修改 .chk（正确偏移 + pad + .blc 更新 + 删清单） | **❌ 完全消失** |

**两次都挂载 `libefml4a_vktex.so`，都是启动后 20-22 秒抓日志。**

## 69.2 结论

```
★★★ 游戏检测到了 .ab 的修改，【跳过】了这个纹理的上传

⇒ 不是流偏移问题（已用正确的 14768）
⇒ 不是容器损坏（目标区验证 TRUE，总长不变）
⇒ 不是 .blc 问题（contentMD5/dataMd5 都更新了）
⇒ 不是校验拦截（游戏没报错、没崩溃、正常启动）

⇒ 是游戏在加载 .ab 时【发现结构不一致，静默跳过】
```

## 69.3 最可能的原因：`compBI` 必须完全相同

**原始 .ab：**

```
compBI = 101
uncompBI = 137
blocksCount = 1
块0: comp=9646 uncomp=24560
dataStart = 160
```

**我的 mod .ab：**

```
compBI = 102      ← ★ 变了 1 字节！
uncompBI = 137
blocksCount = 1
块0: comp=9027 uncomp=24560   ← 数据块压缩后更小
dataStart = 160   （align16(101)=align16(102)=112 ⇒ 不变）
```

**abpack 的 pad 模式尝试过，但失败了：**

```
[pad] 未压缩 137 → 无法达到原 compBI 101
⇒ 因为重压后的块信息本身就有 102 字节，填充只会变大
⇒ 退回 min 模式 + 零填充
```

## 69.4 为什么 compBI 变大

```
块信息的内容是「每个块的 comp/uncomp 大小表」

原始: 块0 comp=9646
我的: 块0 comp=9027   ← 我的 ASTC 更易压缩

⇒ 块信息里记录的 comp 值从 9646 变成 9027
⇒ LZ4Inv 压缩这段信息后的大小从 101 变成 102
⇒ compBI 无法保持 101
```

## 69.5 可能的解决方向

### 方向 A：让 compBI 恰好等于原值

```
需要让块信息压缩后恰好 101 字节
当前是 102 ⇒ 差 1 字节

方法:
  ① 找一个 1 字节的填充位置，使压缩后变成 101（不可能，填充只增不减）
  ② 改变块信息的编码方式（例如调整某个字段的值，使其压缩后更短）
  ③ ★ 让数据块压缩后【恰好等于】原始 comp（9646）
     ⇒ 块信息内容不变 ⇒ compBI 不变
```

### 方向 B：★ 保持数据块大小不变

```
如果我能让新数据块的 comp 值 = 原始值 9646
⇒ 块信息与原始完全相同
⇒ compBI = 101
⇒ ★ 完全等长、等结构

实现: abpack 的 pad 模式扩展 —— 不仅填充块信息，
     还要填充【数据块】使其压缩后长度恰好等于原 comp

⇒ 这是「双向填充」：数据块 + 块信息都精确对齐
```

### 方向 C：用 vkinject 在运行时替换

```
既然 vktex 能看到 Copy #57 (304x68) 的上传
⇒ 用 vkinject 在 vkCmdCopyBufferToImage 时替换数据
⇒ 完全绕过 .ab 结构校验

前提: 要知道目标纹理的识别特征（尺寸 304x68）
```

## 69.6 ★ 方向 C 最直接

**理由：**

```
1. vktex 已证明能看到 304x68 的上传
2. payload 基础设施已打通（Round 15）
3. 不需要改磁盘文件 ⇒ 永不触发任何校验
4. vkinject 的 payload 已经存在（330KB，内嵌 mod 数据）

只需: 修改 vkinject 的匹配条件为「ext.width==304 && ext.height==68」
```
