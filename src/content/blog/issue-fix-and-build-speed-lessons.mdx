这篇文章记录一段真实的维护窗口：处理若干用户提交的 issue（含一个安全类报告），
然后系统性地优化编译/构建速度。所有结论都来自实测，我把**测量方法**和**踩过的坑**一起写下来，
因为后者往往比结论更有复用价值。

## 一、处理用户报告的 issue

### 1. 先把现象在源码里核对一遍，再谈方案

用户报告"密钥能被同机其它程序读走并解密"。我没有直接开始改加密方式，而是先沿着
"密钥从哪来 -> 怎么加密 -> 密文存到哪 -> 谁能读到"逐点核对源码，确认了完整链路。
核对之后才发现报告者没提到的关键事实：**那道"仅本人可读"的权限收紧在 Windows 上其实没生效** ——
`File.setReadable/setWritable` 在 Windows 映射为 DOS 只读属性，**不设置 NTFS ACL**。

结论：报告的结论可能是对的，但**细节往往需要在源码里重新验证**。

### 2. 桌面端凭据：同一用户是条硬边界

评估过三条路：

| 方案 | 能挡住同用户的读取吗 | 代价 |
| --- | --- | --- |
| 明文文件 + 权限收紧 | 挡不住（只挡同机其它用户、离线拷盘） | 无 |
| 系统凭据库（如 Windows DPAPI） | **也挡不住**：同用户进程一样能调用解密接口 | 需要原生调用依赖 |
| 口令派生密钥（PBKDF2 + AES-GCM 包裹） | **能挡住**：攻击者没有口令 | 每次启动要输一次口令 |

要点是：**"在内存里加密凭据"如果解密密钥也在同一进程里，等于安全表演** ——
攻击者 dump 一次内存就同时拿到密钥与明文。真正改变风险的是"攻击者需要付出什么"，
以及**缩短凭据本身的价值**（短效令牌 + 刷新轮换 + 服务端可撤销）。

### 3. 只关闭真正修好并核对过的 issue

对每条 issue 都区分三件事：**改了什么 / 验证了什么 / 还剩什么未验证**。
例如"关闭 attach 机制"这一条：参数进了包（可解包核对），
但"真机上导堆是否确实被拒绝"我没有设备，就明确写成未验证，并给出对方可执行的一条命令。

### 4. 教训：不要只问"要不要"，要去查"能不能"

有一次小版本发布，我漏掉了 Android 包 —— 因为我在中途问了一句"要不要一起发"，
得到"修复完马上发小版本"的回复后就当作不需要了。**发版前应该去查"能不能打"**：
后来一查，SDK 就在本机、签名配置也在，构建一次十分钟就出包了。
对用户来说，少两个包就是**功能退化**，不是"少做一步"。

## 二、把测量当纪律

### 5. 先量后改，且每项单独测量

编译提速最容易犯的错是"凭感觉说快了"。我的做法：**每改一项就单独测**，
同一条件（`--offline`、daemon 状态一致、机器空闲、同一条命令），记录墙上时间。
否则几项一起改，说不清哪项有效、哪项白干。

### 6. 判断"构建是否还在跑"，别依赖 `ps`

在未挂载 `/proc` 的容器里 `ps` 的输出不可信——我因此误判"构建已经死了"，
然后做出了更糟的动作（见第 14 条）。可靠的判据是**看产物体积/时间戳是否在变化**，
或者看构建工具自己的日志尾部。

### 7. 实测数据（同一台 arm64 机器、同一命令）

| 场景 | 改前 | 改后 | 手段 |
| --- | --- | --- | --- |
| 桌面端 Kotlin 编译（热） | 4.4 秒 | **2.0 秒** | 打开配置缓存 |
| 桌面端打包 jar（全复用） | 7.4 秒 | **2.9 秒** | 同上 |
| 移动端全量构建 | 未测 | 10 分 43 秒 | 基线 |
| 移动端增量构建 | 未测 | **6.9 秒** | 基线 |
| 桌面 GUI 无改动增量构建 | **13~25 秒（每次都付）** | **0.07~0.16 秒** | 换 Ninja |
| 桌面 GUI 清空重建 | 72.5 秒 | **13.0 秒** | 接入 ccache |

## 三、构建工具的坑（干货）

### 8. 独立 Gradle 构建不会继承根 `gradle.properties`

主工程根目录早就开了配置缓存，但桌面端子工程是**独立的 Gradle 构建**（有自己的目录），
读的是自己的 `gradle.properties`，所以一直没吃到这项收益。补一行，热编译 4.4 -> 2.0 秒。
**排查思路**：看到某个子工程"配置阶段特别慢"，先确认它的配置文件在哪。

### 9. Makefile 生成器 + 生成文件 = 每次全量重跑

桌面 GUI 工程用 CMake + Makefile 时，**每次**构建都会重编 QML 缓存并重新链接，
哪怕一行都没改（连续三次 18.7 / 25.1 / 13.2 秒）。根因是 QML 缓存 `.cpp` 的依赖里包含
类型注册产物（`.qmltypes`、`.qrc`），只要上游重跑这条链就整体重跑。
**换 Ninja 直接解决**（无改动时 `ninja: no work to do.`，0.04 秒）。

注意：换生成器只需重新配置构建目录，`cmake --build build`、测试命令、脚本里的可执行文件路径都不用改。

### 10. ccache 的账要算两次：首次变慢，之后很快

| 场景 | 耗时 |
| --- | --- |
| 无 ccache 清空重建 | 72.5 秒 |
| 有 ccache，首次（填充缓存） | 99.4 秒 |
| 有 ccache，缓存热 | **13.0 秒** |

只在**第一次**多付约 27 秒，之后每次清空重建省约 60 秒。如果你只构建一次，它反而更慢 ——
所以采用与否取决于你的工作流。另一个细节：`CMAKE_CXX_COMPILER_LAUNCHER` 必须设在
`project()` **之前**才生效。

### 11. 打包脚本会清空自己的输出目录

把 7 个打包目标共用一个输出目录时，产物会"凭空消失"。原因是每个脚本开头都有
`rm -rf "$OUT" && mkdir -p "$OUT"`。**正确做法：每个目标一个独立目录，跑完再收集发布物。**

### 12. 输入指纹的跳过机制值得先确认

打包脚本自带"输入未变且产物齐全则跳过"的机制。实测：同一目标再跑一次只要 **0.044 秒**。
所以**不要**为了"确保干净"乱加 `FORCE=1`，那是几十秒到几分钟的差别。

### 13. 版本号要三处一致，且清单优先

打包产物自称的版本号优先读 **jar 清单**里的 `Implementation-Version`。
只改代码里的常量会导致"包宣称旧版本"。改完必须**解包核对**：
`dpkg-deb -f x.deb Version`、解压 tar.gz 读 `META-INF/MANIFEST.MF`、
用解压工具拆开自解压 exe 看里面的 jar 与启动脚本。

## 四、我自己犯过的错（最有用的一节）

### 14. 不要在脚本运行中重写脚本文件

打包跑到一半，我为了改脚本直接覆写了它 —— bash 读到半截内容报语法错误，构建中断。
**教训：先停任务，再改脚本；改完 `bash -n` 校验再启动。**

### 15. 文本替换的三个经典翻车

- **替换模板漏写"跳过原行"**：新内容加上了、旧行还在，导致重复声明（我犯了三次）；
- **正则括号未配对**：替换静默失败，一行都没改成 —— 我是靠"目标里噪声行数没变"才发现的；
- **锚点选错**：把代码插进了错误的位置（比如 `for` 循环之前，其中用到了循环变量）。

**通用对策：替换前打印将被替换的区间，替换后核对目标是否真的变了。**

### 16. 量错了对象

排查界面布局时，我把探针指向了"详情面板"的 id，却以为在量"阅读器面板"，
于是得出了错误结论。改探针前**先核对 id 归属**。

### 17. 别相信"看起来完成了"

QML 界面里图片"已加载"不等于"画出来了"：探针显示 `实际绘制 0x0`，
原因是布局只给了面板 2 像素宽。**能测量的中间量（尺寸、命中数、字节数）比"看起来"可靠得多。**
顺带一个前端经验：某些框架把 QML 编译成字节码后，**编译期绑定读不到运行时注入的上下文属性**，
而函数与信号回调可以 —— 修法是把计算放进回调、结果写进被绑定的属性。

### 18. 说法必须跟着实现一起改

发版时我在 release notes 里写了"本版未包含某平台包"，后来补齐了包却忘了改正文开头
（只改了文末），差点留下与事实相反的用户文档。**发布物、变更日志、issue 回复三处要一起核对。**

## 结语

这一轮里最值钱的不是"把编译从 13 秒压到 0.1 秒"，而是几条可迁移的习惯：

1. **先核对再动手**，报告的结论对、细节仍要自己验证；
2. **先量后改，单项对比**，并写清测量条件；
3. **能测量的中间量优先**，少用"看起来"；
4. **未验证的部分主动写明**，比含糊带过更省事；
5. **文档、发布物、回复三处一致**。

希望这些经验对遇到类似问题的读者有用。
