用户在论坛里发一句"我的程序打开后没有文字"，你手上只有一份日志。能不能靠它定位问题，
完全取决于**日志里有没有记录那一行关键信息**。下面是我在实战里总结的三条做法。

## 一、启动就打一行"运行环境摘要"

把这几项一次性打在一行里，远程排查的起点就有了：

```text
[环境] 应用 2.1.8 | 系统 Windows 10 (10.0) | 架构 amd64 | 运行时 Java 21.0.12 | 图形后端 软件渲染 | 字体 微软雅黑（可用字体族 132；中文字体 微软雅黑）
```

为什么这几项值得单独设计：

- **系统与架构**：区分"某个包特有"还是"这台机器特有"；
- **运行时与图形后端**：渲染类问题（无文字、黑屏）第一嫌疑就是后端选择；
- **字体环境**：这是"有界面、没文字"最常见的根因。**要明确报出"是否找到常见中文字体"**，
  而不只是报一个字体族数量 —— 数量正常但缺少中文字体，是完全可能的。

配套的一点：未捕获异常处理里，先把这段环境块打出来，再打堆栈。

## 二、噪声要聚合，不要逐条打印

我拿到的第一份用户日志是这样的：**1342 行里有 895 行**是同一类失败
（某个域名连接被重置），一条一个 URL。有效信息被埋掉，而信息量并没有增加。

做法是把"同类失败"按 **类型 + 异常类名**（或 HTTP 状态码）聚合：

- 首次出现时完整打印（带一个样例 URL）；
- 之后每 N 次汇总一条，附上"同类已出现多少次"。

这样既压掉刷屏，又保留了"这类问题的规模"。同时把高频成功日志降级为调试级别
（默认不打印，由环境变量或参数打开），但**用户动作与关键结果要保留在原级别**：
登录成功、发布成功、下载不可用这类事件，不该被降级。

这里的原则是：**按"它是事件还是细节"分级，而不是按关键字一刀切。**

## 三、失败路径要给出"下一步"

日志的价值不止于"记录发生了什么"，还包括"告诉用户现在该做什么"。
例如当渲染后端初始化失败时，与其只留一堆堆栈，不如补一行：

```text
看起来是渲染后端初始化失败：去掉 JMCOMIC_RENDER=GL 再启动一次
（或把 run.bat 里那行改成 set JMCOMIC_RENDER=）即可回退软件渲染。
```

同理，崩溃时把环境块与建议一起写进日志头部，用户复制一次就够。

## 四、顺便说一个包设计上的教训

有一类"无任何输出"的报告，原因是**打包时替用户做了不该做的决定**：
安装脚本里硬写了"强制使用 GPU 渲染"。当那台机器建不出图形上下文时，
进程在创建窗口阶段就失败，而启动日志写在窗口创建之前 —— 于是用户看到的确实是"什么都没发生"。

**结论**：默认值要选"最可能成功"的那个，把激进选项留给用户显式开启；
并且任何"替用户做的决定"都应当被记进日志，否则远程排查时根本不知道它存在。

## 结语

可诊断性设计其实只有一句话：**假设明天你只能靠这份日志排查，那么今天该往里写什么。**
一行环境摘要、聚合后的噪声、失败路径的下一步 —— 三件事加起来成本很低，
但能把"来回问三轮"变成"一次定位"。
