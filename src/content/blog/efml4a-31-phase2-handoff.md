## 31.2 ✅ 已确证的事实（可直接依赖）

### A. EFMI mod 的 `.buf` 格式（`docs/28` §28.2–28.4）

| 流 | stride | 内容 | 置信度 |
| --- | --- | --- | --- |
| `IB` | 2 B/索引 | `uint16[]` 三角形列表 | ✅ 铁证 |
| `VB0` | **16 B** | `3×float32 位置` + `4 B 打包` | ✅ 位置铁证 |
| `VB1` | **12 B**（部分 8 B） | `(u, v, 0)` UV | ✅ 高 |
| `VB2` | **16 B**（部分 8 B） | `4×u16 权重` + `4×u16 骨骼索引` | ✅ 高 |

**全流不变量**：`流大小 / stride == max(IB) + 1`（11/11 组件成立）

### B. `.ab` 的文件性质（`docs/28` §28.19）

- **全程明文**：熵 **3.5–7.6**（头部/TypeTree 3.5–6.0，数据区 7.0–7.6）
  ⇒ **无压缩、无加密**
- **内层是标准 Unity `SerializedFile` + `TypeTree`，Unity 版本 `2021.3.3`**

### C. `.ab` 的外层容器结构（`docs/28` §28.13）

## 31.5 ▶️ 下一步的具体动作

### 优先 1：重写顺序节点解析器（这是唯一的阻塞项）

```python
# 伪代码
i = START
while i < END:
    # 1) 读控制字节（1-3 个，直到遇到可打印 ASCII 起点）
    ctrl = []
    while not (32 <= seg[i] < 127):
        ctrl.append(seg[i]); i += 1
    # 2) 读 z-terminated 名字
    j = seg.index(0, i)
    name = seg[i:j].decode('latin1'); i = j + 1
    # 3) 名字之后紧跟的若干字节（先打印出来人工判断）
    print(ctrl, name, seg[i:i+32].hex())
```

**要点**：**先在 `+288692` 附近小范围（±200 字节）验证**，
手工核对输出与已知骨骼名是否一一对应；
**不要一上来就跑全文件。**

### 优先 2：确定骨骼记录定长

- 若每条记录 = `[u8 idx][name z][i32 parent][Matrix4x4(64B)]`，
  则记录长度 = `1 + len(name)+1 + 4 + 64`
- **用两条相邻记录的偏移差反推**（`a_M/Spine1` 与 `2_M/clothes…` 的间距）

### 优先 3：解析 TypeTree 读 `m_Channels`

- 对 `+2351` 起用同一解析器；`m_Channels` 的每个通道是
  `{u8 stream, u8 offset, u8 format, u8 dimension}`
- 拿到后与 EFMI 的 `VB0/VB1/VB2` 做映射

### 优先 4：实现重打包

- 按 `m_Channels` 布局，把 EFMI 的顶点数据打包成 Unity `m_VertexData`
- **索引缓冲**：EFMI `uint16[]` → Unity `m_IndexBuffer`
- **纹理**：`.dds`(BC5/BC7) → Unity `Texture2D` 的 `m_TextureFormat` 对应格式
- **部署**：用 `chkpatch` 做等长替换（若长度不同，需研究 `.blc` 重写）

### 31.8.2 ⚠️ 路线修正：放弃「完全解析 `.ab`」

**第 28 轮的失败尝试证明：**

```
✦ 在 +12776 之前搜「m_VertexCount / m_DataSize」→ 【无合理值】
✦ 在 +2937 之后搜「m_Channels 数据（14×4B）」→ 【0 个候选】
⇒ 说明 .ab 使用的是【自定义布局】，
   标准 Unity SerializedFile 的字段排布假设【不成立】
```

**⇒ 继续走「完整解析 ⇒ 重新序列化」这条路，成本极高且不确定。**

### 31.8.3 ★ 改用「原地等长替换」快路（推荐）

**核心思路：不解析结构，直接在**已知的数据区**里做**等长替换**。**

```
已知事实:
  +12800 起是顶点数据（stride 16 B，明文，高熵）
  顶点数 = (数据区大小) ÷ 16
  数据区大小 = 条目总长 − 12800（近似）

操作:
  ① 把 EFMI mod 的顶点数据（VB0，16 B/顶点）【等长】写进游戏 Mesh 的顶点区
     —— 若顶点数不同，则只替换 min(mod顶点数, 游戏顶点数) 个
  ② 用 chkpatch 做等长替换（.blc 不动）
  ③ 重启游戏 ⇒ 观察模型是否变化
```

**优点：**
- **不需要懂 `m_Channels` / TypeTree / 容器结构**
- **等长 ⇒ `.blc` 无需改动 ⇒ 索引与 CRC32 天然有效（已验证的路径）**
- **1–2 轮就可能出可见效果**

**风险：**
- **顶点数/顺序不匹配 ⇒ 模型会**扭曲**（但仍是**可见的变化**，足以证明路径成立）
- **若游戏的 `m_VertexCount` 与实际数据区大小不一致，会读到垃圾/越界**

### 31.8.4 有条件的改进路线

**若「原地等长替换」证明可见，再考虑：**
1. **确定游戏 Mesh 的 `m_VertexCount`**（用「数据区大小 ÷ stride」反推）
2. **确定 EFMI 顶点与游戏顶点的**顺序对应**（可能需要重排索引）**
3. **最终才做「完整重打包」**

### 31.8.5 结论

> **第 2 阶段的核心难点不是「格式未知」，而是「`.ab` 用自定义布局，
> 导致标准 Unity 工具链无法直接使用」。**
>
> **⇒ 最经济的路径是「原地等长替换」—— 绕开结构解析，直接用已验证的
> `chkpatch` 机制。**

## 31.10 第 31 轮：索引缓冲定位失败 + 路线澄清

### 31.10.1 尝试与结果

**目标：定位游戏 Mesh 的**索引缓冲**（为「差一步」的顶点/索引对齐做准备）**

```
方法 1：搜「uint16 索引缓冲」窗口（max 合理 + 值分布广）
  结果：4680 个候选 —— 【无区分度】（随机数据也满足）

方法 2：搜「每 3 个 u16 构成合法三角形且索引 < 60000」
  结果：159 个连续区段 —— 【疑似巧合】（随机数据产生合法三角形的概率不低）

方法 3：直接看 +12800 之后的 u16 解读
  结果：值域 0..65000，分布杂乱
  ⇒ 与 §28.30 的 float 解读（±0.3，合理坐标）对比，
    【+12800 是顶点数据（float），不是索引数据】
```

**⇒ **索引缓冲不在 `+12800` 附近**，定位方法需要改进。**

### 31.10.2 路线澄清（重要）

**当前成功的机制：**
```
「直接覆盖前 N 个顶点」⇒ 模型变化（但扭曲）
```

**为什么扭曲：**
```
游戏的三角形索引 I = [i0, i1, i2, ...] 指向顶点 V[0..n]
我们把 V[0..7911] 换成了 EFMI 的顶点
⇒ 索引仍指向【原有编号】，但编号对应的顶点已被替换
⇒ 三角形连接错误的顶点 ⇒ 模型扭曲
```

**⇒ 要修好，需要**二者之一**：**

| 方案 | 做法 | 成功率 |
| --- | --- | --- |
| **A. 只换顶点，不动索引** | **让 EFMI 的第 k 个顶点对应游戏的「第 k 个索引所引用的顶点」** ⇒ 需要**重排** EFMI 顶点顺序 | 高（但需先读出游戏索引） |
| **B. 同时换索引与顶点** | **把 EFMI 的 IB 也写进游戏的索引区** ⇒ 需定位索引区 | 中（需定位） |
| **C. 保持当前「直接覆盖」** | **接受扭曲** | ✅ 已成功（证明路径） |

### 31.10.3 下一步（更有效的方法）

**不再盲目搜索引，而是：**

1. **用 EFMI 的 `m_LocalAABB` 匹配法**：
   EFMI 的 `Component0` 有自己的包围盒（可从 `VB0` 算出 min/max）
   ⇒ 与游戏 `Mesh` 的 `m_LocalAABB`（`+12776`，已读出）**做匹配**
   ⇒ 找到「哪个游戏 Mesh 对应 EFMI 的 Component0」

2. **用「顶点位置分布」匹配**：
   对游戏顶点区做**位置直方图**，与 EFMI Component0 的位置直方图对比
   ⇒ 相似的区域 ⇒ 对应同一个部件

3. **优先做「方案 A」**：
   **重排 EFMI 顶点**使其顺序与游戏一致
   —— 比定位索引更容易（只需顶点的空间对应关系）
