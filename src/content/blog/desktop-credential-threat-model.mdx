一个桌面应用如果要"记住登录状态"，就必须把凭据落到本机。这类设计几乎一定会收到
"同机程序可以读走凭据"的报告。下面是我处理这类报告时使用的威胁模型与取舍，
以及为什么最后没有选择看起来最"硬"的那个方案。

## 一、先把链路核对清楚

报告通常只说结论。动手前应当沿着源码把这几步都走一遍：

1. 凭据在**应用层**怎么加密（算法、模式、打包格式）；
2. **密钥从哪来**（生成方式、存在哪、谁能读）；
3. **密文存到哪**（配置文件、系统偏好、注册表）；
4. 攻击者需要哪些前提（同用户？同机？能执行代码？）。

核对之后常常会发现报告者没提到的关键细节。例如我遇到的真实情况是：
代码注释写着"权限已收紧为仅本人可读"，而那两个收紧权限的 API 在 **Windows 上只映射为
DOS 只读属性、并不设置 NTFS ACL** —— 也就是说在报告针对的平台上，这道防护其实没生效。

## 二、威胁模型：先分清攻击者

| 攻击者 | 能否防住 | 靠什么 |
| --- | --- | --- |
| 同机其它用户 | 能 | 文件权限（POSIX 的 600；Windows 的 ACL 移除宽泛主体） |
| 拷走磁盘或备份后异地读取 | 能（开启口令后更强） | 同上；口令保护下拿到文件也解不开 |
| 本机同一用户的普通程序 | **只有口令保护能挡住** | 攻击者没有口令，就没有解开密钥的材料 |
| 同一用户下的恶意软件 / 注入进程 | **防不住** | 它能读内存、能等用户输入口令、能调用同样的系统接口 |

关键判断：**只要攻击者能以同一用户身份执行代码，本地存储的凭据在原则上就守不住。**
所以目标不该定成"杜绝"，而应定成"提高攻击成本 + 缩短凭据价值"。

## 三、为什么不做"系统凭据库"，也不做"内存加密"

很多人第一反应是接入系统凭据库（Windows DPAPI、Linux libsecret、macOS Keychain）。
它确实有用，但要看清它挡的是哪一类：

- 它能挡住"**换用户**"和"**离线拷盘**"—— 因为解密的密钥材料绑定在登录凭据上；
- 它**挡不住"同用户进程"** —— 同一个用户下运行的任何程序都能调用同一个解密接口。

既然它挡住的那一类，权限收紧（ACL）已经能挡，而它还需要引入原生调用依赖，
我最后选择了**口令派生密钥**：用 PBKDF2 从用户口令派生包裹密钥，再用 AES-GCM 把真正的
数据密钥包起来。这样攻击者没有口令就拿不到密钥材料。

而"**在内存里加密凭据**"我没有做：解密密钥如果也在同一个进程里，
攻击者 dump 一次内存就同时拿到密钥与明文 —— 那是安全表演，不是防护。

## 四、三层措施（可落地）

1. **权限收紧**：POSIX 用 `chmod 600` 语义；Windows 用 `java.nio` 的 ACL 视图
   **移除宽泛主体**（Users / Authenticated Users / Everyone 等）。
   注意策略要保守：**只删宽泛主体**，不动所有者与系统账户；异常时只告警、不改动原 ACL。
2. **口令保护数据密钥**：`salt || iv || AES-GCM(密钥)`，派生迭代次数写死在代码里；
   **口令错误要 fail closed**（拒绝读写，而不是退化成明文）。
   默认策略上我选了"**全新安装默认开启、可拒绝、老安装不变**"——
   只有全新安装是能无痛改变默认的人群，老安装强制切换会造成"登录状态丢失"。
3. **登出即销毁密钥材料**：只清键值存储却留下密钥文件，等于"换了锁但钥匙还挂在门上"。

## 五、真正降低风险的方向

如果要在威胁模型上再进一步，靠的不是客户端存储技巧，而是**缩短凭据的价值**：

- 短效访问令牌 + 刷新令牌轮换；
- 服务端可撤销（登出、改密后旧令牌立即失效）；
- 或者干脆不持久化会话，重启即要求重新登录。

这些需要服务端配合，但它们比继续加固本地存储更有效。

## 结语

一句话总结这类问题的处理原则：**先把攻击者分类，再判断哪些措施真正改变了攻击成本；
对防不住的那一类，明确写进文档，而不是用看起来复杂的方案掩盖它。**
