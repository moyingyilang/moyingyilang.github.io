[JMNeXt](https://github.com/moyingyilang/JMNeXt) 是一套单源客户端。
[TriComiX](https://github.com/moyingyilang/TriComiX) 在它之后立项，定位一句话：

> 一个核心，多个可插拔内容源。

三家的协议性质完全不同：一家是私有 API 加客户端签名，一家是私有 API 加请求签名与时间同步，
一家是网页站点加登录态、分页与反爬。把它们塞进同一套界面，先要回答的不是"协议怎么写"，
而是"接口在哪里划线"：哪些字段进统一模型，哪些差异留在源里，界面凭什么决定显示哪个入口。

文章里的判断有两条来源：仓库的 `docs/design.md`（自身标注为**草案，尚未落地**）
与 README 记录的当前状态（`0.2.0-preview`）。两者不一致的地方，下文会分别标出来。

## 1. 为什么必然是重写重实现

先看参考实现这一侧。能不能复用代码，不取决于"功能像不像"，只取决于技术链与许可证。

| 参考实现 | 技术链 | 代码能否复用 |
| --- | --- | --- |
| JMComic 客户端（存档） | Java + `android.support.*` 26 + Sugar ORM + ButterKnife | 不能 |
| `raoxwup/haka_comic`（★1.5k） | Dart/Flutter，**GPL-3.0** | 不直接复用；但许可允许并入 AGPL 项目（需署名） |
| Pica 客户端若干 | Dart / Python-Qt / TypeScript | 不能 |
| EhViewer 系列 | Java / Kotlin，但**多数无许可证** | 不可（默认保留所有权利） |

第一列里没有一家的技术链和本项目（Kotlin + Compose Multiplatform）相同。
`android.support.*` 26 与 ButterKnife 那一套已经停更，Dart/Flutter 与 TypeScript 是另外的运行时，
Java/Kotlin 那家恰好又是许可证最紧的一家。

技术链差异决定了只能做**协议级重实现**。许可证层面真正起作用只剩两条：

| 许可证情形 | 约束 |
| --- | --- |
| GPL-3.0（如 `haka_comic`） | 可以并入，但需署名 + 同许可；本项目 AGPL-3.0 满足同许可 |
| 无许可证（EhViewer 系列多数） | 只能当**行为参照**，不得并入任何代码 |

技术栈不同还可以照抄算法，许可证不允许就是不允许。第 6 节把这条展开成五条工程规则。

## 2. `ComicSource`：接口长什么样

接口落在 `core` 模块，只依赖标准库，可以离线构建。实际代码（已比草案多出几项）：

```kotlin
interface ComicSource {
    val id: String
    val displayName: String
    val capabilities: Set<Capability>

    suspend fun login(credential: SourceCredential): Result<Session>
    suspend fun logout()

    suspend fun home(): Result<List<Section>>
    suspend fun search(query: String, page: Int): Result<Paged<Comic>>
    suspend fun detail(comicId: String): Result<ComicDetail>
    suspend fun chapters(comicId: String): Result<List<Chapter>>
    suspend fun pages(chapterId: String): Result<List<PageRef>>
    suspend fun imageRequest(page: PageRef, quality: ImageQuality): Result<ImageRequest>

    suspend fun favorites(page: Int): Result<Paged<Comic>>
    suspend fun history(page: Int): Result<Paged<Comic>>

    suspend fun toggleFavorite(comicId: String): Result<Unit> =
        Result.failure(SourceError.Unsupported("该源不支持修改收藏"))
}
```

草案里的接口没有 `displayName`、`FOLLOW`、`FAVORITE_WRITE` 与 `toggleFavorite`，
这四项是落地过程中补的；`docs/design.md` 的正文还没同步回去。

### 2.1 全部 `suspend` + `Result`，异常不上抛

约定写死在接口注释里：源的实现**不向界面层抛异常**，一律返回 `Result.failure`，
异常类型收敛成一个密封类：

| 错误类型 | 含义 |
| --- | --- |
| `Network` | 网络层失败 |
| `Auth` | 凭据失效或未登录 |
| `NotFound` | 目标不存在 |
| `Parse` | 响应形状与预期不符 |
| `Unsupported` | 该源不支持此能力 |
| `Unknown` | 兜底 |

这么定的理由很实际：界面层不需要为每个源写 try/catch，也不需要区分 `IOException` 与解析越界。
配套的一条是**失败要能定位**：命令行探针在每一步失败时会打印失败的环节与错误类别，
不把失败表示成空结果。空结果和"解析失败"在界面上长得一样，在排查时差别极大。

### 2.2 `PageRef` / `ImageRequest` 这层间接为什么必需

这是整个接口里最关键的一处划线。三家取图方式的差异：

| 源 | 取图方式 | 为什么不能在统一模型里直接存 URL |
| --- | --- | --- |
| JM | 图片**被打乱**，需按算法还原 | 还原算法是源私有逻辑，界面不该知道，也不该在界面里重写一遍 |
| EH | 按分页组织，每张图带一个**会过期**的 `hath` 键 | 键是短时凭据，固化进统一模型就会把"过期"变成界面问题 |
| Pica | 同一章有多个**质量档位**，取图前先要决定档位 | 档位是请求参数而不是资源属性，只能作为 `imageRequest` 的入参 |

所以模型里存的是 `PageRef`（"第几页的什么东西"），要真正下载时再调 `imageRequest(page, quality)`
换一个 `ImageRequest`（"此刻该用什么请求去拿"）。多这一层，换来三件事：

1. 界面拿到的是**页序列**，不需要假设每个源都有章节；
2. 过期键、打乱算法、质量档位都被关在源实现里，不会泄漏到界面；
3. 换源时不改界面代码。

### 2.3 统一模型只放三家都能表达的字段

- 字段进统一模型的唯一条件是：三家都能表达。任何一家表达不了的，不进模型。
- 源特有字段进 `extra: Map<String, String>`，**不做万能模型**。
- 万能模型的代价是每个字段都要在界面上解释"这家有没有"，最后等于把三家差异搬到界面层。

## 3. 统一模型与三家映射

草案里给出的映射表：

| 概念 | JM | Pica | EH |
| --- | --- | --- | --- |
| 作品 | album | comic | gallery |
| 章节 | chapter | chapter(eps) | ——（EH 是"分页"而非章节） |
| 阅读单元 | chapter | chapter | page（每页含若干图） |
| 图片地址 | 需按算法还原 | 直链（带质量档） | 直链 + `hath` 键（会过期） |
| 登录 | 账号 | 账号 | cookie（并需注意站点访问限制） |
| 收藏 | 服务端 | 服务端 | 服务端 |

表里只有"作品"和"收藏"这两行是三家的形状真正一致的。其余四行都带着一处无法拉平的地方。

### 无法统一的点要提前认账

| 无法统一的点 | 具体表现 | 界面的应对 |
| --- | --- | --- |
| EH 的"页"与另两家的"章" | 不是同一个概念，硬套会出现"每章一页"或"一章多页"的假象 | 界面消费"页序列"，不假设每个源都有章节 |
| JM 的打乱图 | 源私有还原逻辑 | 收在 `imageRequest` 里，界面只拿 `ImageRequest` |
| Pica 的质量档位 | 另两家没有对应物 | 作为请求参数传入，不写进作品或章节模型 |

一件事在文档里写清楚"这里不统一"，比在代码里假装统一要便宜得多。

## 4. 能力位 `Capability` 与界面按能力显隐

规则只有一条：**界面仅依据能力决定入口显隐，不按源名做特判**。

| 能力位 | 含义 | 当前状态 |
| --- | --- | --- |
| `LOGIN` | 可登录 | 三家都有 |
| `SEARCH` | 可搜索 | 三家都有 |
| `HOME` | 有首页分区 | 草案未说明；README 记录 Pica 首页**未验证/不实现** |
| `FAVORITES` | 可读取收藏列表 | JM、EH 有；EH 收藏读取已实现但未在真实环境使用 |
| `HISTORY` | 有历史 | Pica 与 EH 的历史**不实现**（相关端点在任何可得资料中均不存在） |
| `DOWNLOAD` | 可下载 | 能力位已定义 |
| `FAVORITE_WRITE` | 可**修改**收藏（加/取消），只读列表用 `FAVORITES` | 接口已扩展，目前仅 JM 源接入 |
| `FOLLOW` | 可"追更" | **目前无源实现，因此侧栏的追更入口被剪空** |

源不具备的能力，对应入口会被移除或显示"该源不支持"，**不保留点了没反应的控件**。
`FOLLOW` 是这条规则最好的例子：能力位留着，实现没有，于是入口干脆不出现——这是刻意的，不是漏做。

### 4.1 用默认实现做接口演进

`toggleFavorite` 的做法值得单独记一笔：它在接口里给了**默认实现**，直接返回 `Unsupported`
（实现就是第 2 节代码块的最后两行）。于是没覆盖它的源，编译与行为都不受影响，
不用为加一个方法改三个实现类；界面那边只看 `FAVORITE_WRITE` 决定是否显示入口。

语义上也选了"切换"而不是"设为某状态"，因为最底层的实现本来就是切换语义：JM 的
`JmRepository.toggleFavorite` 与 EH 的收藏表单都是这个语义，包装成"设为 true/false"反而要在客户端维护一份状态。

## 5. 凭据与隐私：一处实现，三家受益

统一的不只是界面，还有凭据保护。所有源统一走既有的 `SecureStore` + `SecretKeyProvider`：
**口令保护一处实现，三家受益**（这是 issue #12/#14 那套工作的直接复用）。

规则与现状要分开看，别混成一件事：

| | 内容 |
| --- | --- |
| 设计规则（草案） | 任何服务端凭据/密钥都不进仓库（含 git 历史）；第三方签名密钥一律**运行时提供**（环境变量或本地文件）；缺失时明确报错；文档、日志、提交信息中都不出现密钥值 |
| 当前实现（README） | Pica 需要的两个常量当前**直接内置**在源的源码里，仓库保持公开；环境变量与本地文件仍可覆盖 |

README 对这件事的说明是：该签名密钥在此前一次推送中已经暴露，
因此写入仓库并未新增暴露面；但仓库公开意味着**任何人都可以取得这两个值**。
它属于对方客户端、不属于本项目可轮换的对象，只能作为已知事实记录。

运行时覆盖的写法（取值一律用占位符）：

```bash
export TRICOMIX_PICA_APIKEY=…
export TRICOMIX_PICA_SIGNINGKEY=…
# 或写入 ~/.tricomix/pica-keys.properties（apiKey=… / signingKey=…）
```

**取值缺失或为空时不会静默失败**，而是明确报错并指出需要设置的变量。
这一条是踩过坑才加的：静默失败的表现是"签名持续被拒"，从现象追到环境变量要花很久。

## 6. 工程规则五条

这五条写进 `docs/design.md` 第 7 节，标注为**不可协商**：

| 序号 | 规则 | 要点 |
| --- | --- | --- |
| 1 | 重实现，不搬运 | 引用协议时用**描述**，不贴原代码 |
| 2 | 确需并入 GPL-3.0 代码 | 署名 + 同许可（AGPL-3.0 已满足）+ 文件头注明来源 |
| 3 | **绝不**并入无许可证项目的代码 | EhViewer 系列多数无许可证，属明确禁区 |
| 4 | 原 APK 与反编译产物不进本仓库 | 包括作为参考资料临时提交 |
| 5 | 不逐行翻译反编译产物 | 逐行翻译仍属衍生，只依协议文档与行为观察重写 |

第 4 条与第 5 条容易被当成形式主义，实际是同一件事的两面：只要承认"读了反编译产物"，
就已经在许可证的灰区里；把反编译产物放进仓库，还会连带仓库本身。

EH 源的实际情况可以当例子：它参考的是一份第三方分支的反编译产物（应用包名
`com.xjs.ehviewer` 2.0.2.3），**仅作结构阅读与协议参考**；解析与请求链路均为自行重写，
不复制其代码。同一段致谢里也写明 `haka_comic`（GPL-3.0）只贡献了屏蔽与列表过滤的设计思路，未共用代码。

## 7. 命名记录

名字是需求的一部分：它要能放进包名与可执行文件名，也要能对外描述而不带来额外关联。

| 片段 | 含义 |
| --- | --- |
| `Tri` | 三个源统一在一个客户端里 |
| `Comi` | 漫画（comic） |
| `X` | cross（跨平台、跨源）；与既有项目 `JMNeXt` 的收尾大写 X 呼应 |

对应到具体标识：仓库名 `TriComiX`，包名/命名空间 `com.tricomix`，可执行文件 `tricomix`。

### 7.1 查重结论（建库前已执行）

| 查询 | 结果 |
| --- | --- |
| GitHub 仓库名 `tricomix` | 无任何同名仓库 |
| 漫画阅读器领域 `tricomix comic` | 无占用 |
| `ComiX` 系列（`comix reader` 等） | 只有若干零星小项目，无同名者 |

### 7.2 两条硬约束

1. **绝不出现成人向三字母缩写片段**——会把关联重新带入仓库元信息（本文按同一条约束，
   不复写该片段，候选名单里的对应项也只记"命中第 1 条"）；
2. **不保留完整的商标式片段**——既有商标问题，也会把成人向关联写进元信息
   （主项目曾因此类关联在搜索引擎中难以被发现）。

按这两条，被否决的候选包括 `Vica`、`Picomi`（残留商标片段），以及一项命中第 1 条的候选。

### 7.3 对外元信息与已知取舍

仓库描述固定为 `A Kotlin/Compose Multiplatform comic reader with pluggable sources.`，
topics 为 `kotlin`、`compose-multiplatform`、`android`、`desktop-app`、`comic-reader`、`multi-source`；
三个源的名字**只出现在代码模块名、文档与提交信息里**，不进描述与 topics。

两处已知取舍：

- `ComiX` 的写法与 ComiXology 有一点联想（个人项目可接受；若在意可退化为 `TriComic`，
  代价是失去与 `JMNeXt` 的家族感）；
- `Tri` 把"三家"写进了名字——将来若扩到第四家源，名字会比功能"老"。

## 8. 还没做完的，写在明面上

多源架构的价值在于"一个核心"，但当前状态离"完成"还有距离。以下都是 README 里明确记着的：

| 项目 | 状态 |
| --- | --- |
| 会话跨重启 | **不支持**：Pica 令牌与 EH cookie 仅存在于运行内存中，重启后需重新登录 |
| 搜索的排序、日期筛选、热词与随机推荐 | `ComicSource` 中没有对应位置，界面暂不显示（底层能力已具备，缺的是接口层的位置） |
| EH 收藏写入 | 接口已补 `FAVORITE_WRITE`，仅 JM 源接入 |
| EH 登录与收藏读取 | 已实现，未在真实环境使用 |
| Pica 首页与历史、EH 历史 | 不实现（相关端点在任何可得资料中均不存在） |
| `app-desktop` | 尚未建立，界面适配先在 Android 上进行 |
| Qt 线是否支持多源 | 待决策；`JMNeXt4QtDesktop` 目前无 LICENSE 文件（默认"保留所有权利"，与主项目 AGPL 定位冲突） |

验证口径也要一起记：单元测试 168 个（JM 56 / Pica 40 / EH 72）全部通过，
另有 12 项不联网自检。但这些单测用的是**自写的合成样本**，
只能证明"解析逻辑对给定形状自洽"，不能证明"真实页面即为该形状"；
每一项可用性结论都另有真实响应核对。把这句话省掉，测试数字就会变成过度承诺。

## 9. 小结

划接口边界的顺序，基本就是这篇文章的顺序：

| 步骤 | 产出 |
| --- | --- |
| 先判许可证 | 决定哪些参考实现只能当行为参照 |
| 再定接口 | 全部 `suspend` + `Result`，异常不上抛 |
| 再挖间接层 | `PageRef` 与 `ImageRequest` 吸收三家取图差异 |
| 再定模型 | 只放三家都能表达的字段，源特有字段进 `extra` |
| 再定显隐 | 界面按 `Capability`，不留无响应的控件 |
| 最后认账 | 无法统一的点、未验证的项、待决策的项，全部写进文档 |

同一套界面已经跑在三家源上。读者如果关心界面层怎么搬迁，可以看
[/blog/compose-to-qt-1-inventory](/blog/compose-to-qt-1-inventory) 那一系列；
关心单源客户端本身的演进，看 [/blog/jmcomic-next-changelog](/blog/jmcomic-next-changelog)。
