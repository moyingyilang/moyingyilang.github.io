项目是 [JMNeXt](https://github.com/moyingyilang/JMNeXt) 的 C++/Qt 桌面端重实现
（仓库：[JMNeXt4QtDesktop](https://github.com/moyingyilang/JMNeXt4QtDesktop)）。
UI 层最初定的路线是"一对一复刻 Compose 界面"，也就是全部走 Qt Quick / QML。
真正动手之后改成**混合方案**：Widgets 为主体，只在少数几处嵌 QML。

这一篇写的是做这个决定时需要事先想清楚的事：边界划在哪、共用层为什么必须是静态库、
后端怎么把工作线程接给 QML，以及一条我在动手前没意识到、动手后才被迫搞明白的线程规则 ——
**图像提供器不在界面线程里被调用**。

## 一、混合方案的边界：哪四项非 QML 不可

划边界之前先做了一次动效清点，把主项目里每一项动效按"Qt 能不能做到"定级：
QSS 与 `QPainter` 能表达的算 (b)，需要自绘但可行；只有 QML 原生能表达的算 (c)。
结论是只有四项落在 (c)，其余都能在 Widgets 侧做完：

| 动效 | 主项目行为 | 为什么 Widgets 不行 | QML 侧是什么 |
| --- | --- | --- | --- |
| 表面按压回弹 | `spring(dampingRatio = 0.55f, stiffness = 900f)` | 只有解析曲线 `QEasingCurve`，`OutBack` 只能近似过冲，要真弹簧得自己写积分器 | `SpringAnimation` 内建 |
| 胶囊吸附 | 松手后吸到最近一栏，`spring(0.72f/420f)`，非弹簧风格为 `spring(1f/300f)` | 同样缺弹簧积分器，还要自己接拖动与松手 | `Behavior on x { SpringAnimation {} }` |
| 胶囊拖起放大 | 拖动中 1 → 1.04 倍，`spring(0.45f/900f)` | 缩放能做，做出这套手感不行 | 同上，一行 Behavior |
| 列表条目位移 | Compose 的 `animateItem()`，增删/换位时逐条位移 | `QListView` 没有条目级布局动画，要做等于从零写一个自绘列表（含回收复用） | `ListView` 的 `add`/`remove`/`move`/`displaced` transition |

这四项都在"悬浮底栏 + 列表"这一小块界面上，所以它们决定的是**局部嵌 QML**，
而不是"整个应用改用 QML"。反过来，阅读器、章节列表、搜索这类以文本与图片为主的区域，
Widgets 的质量与工作量都更可控，没有理由为了统一而重写。

一条实现期的约束记在这里：容器里是 Qt 6.4.2，`MultiEffect` 要 6.5+，
所以清点里那些"模糊/颗粒"的效果在 QML 侧也还没有现成件，要么走 Qt5Compat，要么自写 shader。
**这也是当初反对"全量重写"的理由之一**：重写了并不自动获得主项目那套观感。

## 二、共用层为什么必须是静态库

两个前端（`jmnext4desktop` 与 `jmnext4qml`）都需要同一批能力：网络客户端、磁盘与内存缓存、
图片解码、后台 worker。如果各写一份，除了重复劳动，还会出现"一边修好的 bug 另一边还在"。
所以这些被抽成一个静态库 `jmnext_qtlayer`，五个源文件：

- `JmClient`（会话与业务请求）、`QtHttpClient`（传输）；
- `ImageCache`（内存 LRU + 磁盘原始字节）、`ImageCodec`（解码）；
- `JmWorker`（跑在后台线程的工作对象）。

`jmnext_qtlayer` 刻意**不含** `MainWindow.cpp` —— 那是 widget 专属界面；
QML 侧由 `JmBackend` 复用同一个 `JmWorker`。判断标准可以压缩成一句：
**如果一段代码在两个前端里应当表现完全一致，它就不该待在前端目录里。**

共用层与调用方向的完整论证在[共用层、后端桥与图片进界面](/blog/qt-port-architecture)里，这里只记结论。

## 三、后端桥：worker 在工作线程，QML 只调 Q_INVOKABLE

`JmClient` 的方法都是同步的，一次列表或一页图是几百毫秒到几秒不等，放在界面线程会卡住界面。
做法是把 `JmWorker`（含网络客户端）移进独立线程，`JmBackend` 只做三件事：

| 事项 | 做法 |
| --- | --- |
| 让 QML 能调 | worker 的槽一对一包成 `Q_INVOKABLE`（`loadList` / `loadMore` / `loadAlbum` / `openChapter` / `step` / `loadCovers` 等） |
| 不阻塞界面 | 全部走队列连接投递到工作线程；`JmBackend` 不复制任何业务逻辑，只转发 |
| 网络管理器的线程归属 | `QNetworkAccessManager` 必须在**使用它的线程**里创建，所以由 worker 在工作线程内惰性创建 |

需要把数据交给 QML 绑定时，有一条已经踩过的坑：**上下文属性（context property）不是信号**，
`Connections` 接不到它的变更，编译后的绑定也读不到运行时注入的值。
正确做法是带 `Q_PROPERTY(..., NOTIFY ...)` 的小 QObject。
这个坑的完整排查过程在[三个最花时间的坑](/blog/compose-to-qt-4-hard-pitfalls)第一节，不重复。

桥接是否真的通了，用自检模式量而不是看日志：

```sh
QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software ./build/jmnext4qml --selftest
```

实测拿到**列表 80 条**，以及**真实一页图 852x1280**（阅读页整页图，WebP 解码后）。

## 四、图片进 QML：提供器跑在渲染线程（本篇重点）

QML 的 `Image` 只吃 URL，所以"QML 显示封面"看上去是加一个 `QQuickImageProvider` 就完事。
我原本把它当成"加个 provider"的小事，直到把 API 的线程语义确认清楚，才知道这里的约束是硬的：

> `QQuickImageProvider::requestImage` 是在 **Qt Quick 渲染线程**里被调用的，不是界面线程。

这一句直接否掉两条"最省事"的写法：

1. **不能直接用 widget 侧那个 `JmClient` 实例**。它的 `QNetworkAccessManager` 有线程归属，
   必须在创建它的线程里使用；在渲染线程里发起请求是未定义行为，不是"慢一点"。
2. **不能直接用 `ImageCache` 的内存 LRU**。那个 LRU 不是线程安全的（它由界面线程一侧的
   worker 写入），渲染线程并发访问会坏。

### 可行做法：提供器只读磁盘缓存

最终实现里，提供器**只用磁盘缓存**，并且用自己的一个 `ImageCache` 实例，
只调 `hasRaw / raw / putRaw` 这类磁盘接口，完全不碰内存 LRU：

| 环节 | 谁负责 | 在哪个线程 |
| --- | --- | --- |
| 下载图片字节 | worker 的 `JmClient` | 工作线程 |
| 写磁盘缓存（原始未解码字节） | worker 的 `ImageCache` | 工作线程 |
| 读磁盘缓存 | 提供器自己的 `ImageCache` 实例 | Qt Quick 渲染线程 |
| 解码 | `QImage::loadFromData` 直接解原始字节 | Qt Quick 渲染线程 |

提供器实现里唯一一件"业务"的事是拼 URL，而这里恰好是最容易出错的地方。

### 缓存键必须与写入方逐字一致，`?v=` 不能去掉

`ImageCache` 的磁盘缓存键**就是完整 URL**，形如：

```text
<imageBase>/media/albums/<id>_3x4.jpg?v=<updateAt>
```

（由 `core/JmUrls.cpp` 的 `coverUrl()` 生成，`updateAt` 非空时才追加 `?v=`。）

于是有一条硬结论：**提供器必须算出与 worker 完全一致的 URL 才能命中同一份磁盘缓存**。
这里有一种看起来更省事的做法：把 `?v=` 从缓存键里去掉 —— 那样确实更容易命中，
但那个版本号的作用就是让封面在服务端更新后失效；去掉它等于让用户长期看到旧封面，
**这是行为回退，不是优化**，所以没做。

### 由此得到的架构结论：后端必须把 URL 交出来

顺推下来，问题变成：QML 侧怎么知道那个 URL？

- 最初的信号是 `listReady(titles, ids)`，**里面没有 `updateAt`**，QML 根本没有拼 URL 的原料；
- 所以后端必须把 `updateAt`（或直接给出完整封面 URL）暴露给 QML。

实现上给 `JmClient` 加了 `coverUrlFor(entry)`，对外给出的 URL 与内部取图用的是同一段逻辑
（`core::coverUrl(entry.id, entry.image, entry.updateAt, imageBase)`），
再由 `JmWorker` 在 `coverReady` 之前发出 `coverUrlReady(index, url)`。
QML 侧因此写成 `image://jm/cover?<percent-encoded url>`，**提供器自身无状态**，
id 里带着它需要的全部信息。

详情页封面走的是另一个 id 形式 `albumcover?<aid>`：它由 aid 走模板拼 URL，
**不带 `?v=`** —— 因为详情接口那条路径本来就不带版本参数，只有与写入方规则一致才能命中。
两个 id 形式看起来不一致，但规则是同一条：**缓存键必须与写入方逐字一致**。

### 缓存未命中：返回占位图，而不是空图

这是必备的降级路径。返回空图时 QML 只在控制台报一句加载失败，
界面上是一块空白，用户与开发都不知道发生了什么。所以未命中返回一张纯色加边框的占位图，
尺寸随请求（默认 120x160）。

### 实测（自检模式，真实网络）

| 检查项 | 实测 | 说明 |
| --- | --- | --- |
| 列表条数 | 80 条 | 后端链路通 |
| worker 取到封面 | 400x533，且拿到 URL | `coverUrlReady` 生效 |
| 提供器按**同一 URL** 取图 | 400x533 | worker 写盘、提供器读盘，**跨实例命中** |
| 提供器按不存在的 id 取图 | 120x160 | 占位图路径生效，不崩溃 |

第三条是这条设计的关键证据：它证明的不是"返回了一张图"，而是"渲染线程读到了工作线程写的同一份磁盘缓存"。

### 阅读页图为什么走另一条路

页图没有走提供器，而是由 GUI 线程把解码结果落成临时 PNG，再用带 `NOTIFY` 的属性
把路径暴露给 QML（`pagePath` 与 `pageSeq`）。理由是页图的 URL 来自章节数据、
下载本来就由 worker 完成，而且阅读页需要"就绪 / 未就绪"的状态感 ——
用属性带状态比让 `Image` 自己去猜更清楚。两条路径并存是权衡的结果，不是没统一。

## 五、一次真实布局故障：探针数据与结论

布局故障本身（侧栏写了首选宽度，内部子项的隐式/最小宽度把整行分配顶满）在
[三个最花时间的坑](/blog/compose-to-qt-4-hard-pitfalls)第二节已经写过，这里只补那篇没有的量：

| 时刻 | 窗口 | RowLayout | 左栏 | 右栏 |
| --- | --- | --- | --- | --- |
| 修前 | 1180x780 | 1180x780 | 1178 | **2x780**（2 恰等于 spacing，即分到 0） |
| 修后 | 1180x780 | 1180x780 | 380 | **800x780** |

页面加载成功却画在 2 像素宽的区域里，所以"日志说加载成功"和"用户看得见"是两件事。
修法是给侧栏补 `Layout.minimumWidth: 380` 与 `Layout.maximumWidth: 380`，把设计意图固定下来。

**不想只靠网络复测**，所以加了一条离线测试通道：`--page <本地图>` 把本地图片直接交给阅读器
（跳过后端与网络）。实测：

```text
--page：已把本地 png（1180x780）交给阅读器
几何：阅读器 800x780，图片 784x734，绘制 784x518
截图 348687 字节（首页列表为 224348）
```

绘制尺寸非零、截图体积从 224348 涨到 348687，说明渲染侧成立。
这条通道把"渲染侧"与"网络侧"分开证明，是整轮排查里最有用的一步。

### 真实网络复测的诚实结论

三项证据分别独立成立：页面能加载（QML 打印过"源 852x1280"）、布局已修好（左 380、右 800）、
渲染路径成立（离线绘制 784x518）。但**"一次运行同时拿到这三项"没有做到**：
多次复测卡在"取章节页图"这一步，而同一时刻 widget 版却能成功，
说明是接口与图床的波动，不是本地代码缺陷。所以我不把"一次运行同时拿到三项"当完成门槛，
那个窗口期不由我控制。

## 六、构建与迭代速度：Qt 特有的那一根因

这一项的完整数字（Makefile 与 Ninja 的对比、ccache 的"首次反而更慢"）在
[构建提速的完整记录](/blog/build-speed-complete-record)里，这里只记 Qt 端特有的根因：

| 场景 | Makefile | Ninja |
| --- | --- | --- |
| 无改动增量构建 | 13~25 秒（每次都要付） | 0.04~0.20 秒 |
| 首次全量重建 | 未测 | 77.3 秒 |
| 清空重建（无 ccache） | 72.5 秒 | 72.5 秒 |
| 清空重建（ccache 热） | —— | 13.0 / 13.2 秒 |

根因不是"Qt 编译慢"，而是 **QML 缓存这个生成文件的依赖链**：`Main_qml.cpp`
的依赖里含 `*.qmltypes`、`.rcc/*.qrc` 与 C++ 类型注册产物，只要 `qmltyperegistrations` 重跑，
这条链就整体重跑并重新链接。Makefile 生成器处理不好"生成文件依赖生成文件"，
Ninja 能正确处理。换生成器只需要重新配置构建目录，`cmake --build build`、
测试命令、脚本里的可执行文件路径都不用改。

ccache 是在 `project()` **之前**检测并设为 `CMAKE_CXX_COMPILER_LAUNCHER` 的（放后面不生效），
账要算两次：首次填充缓存时全量重建 99.4 秒，比不接还慢约 27 秒；之后每次清空重建省约 60 秒
（74/148 命中，约 5.5 倍）。

## 七、性能基线

"首屏到能看第一页"是本项目用户感知最强的一段路径。实测（同一台机器、同一网络）：

| 场景 | 耗时 | 说明 |
| --- | --- | --- |
| 首屏 → 第一页（无任何缓存） | 3685 ms | 主机发现 + 详情 + 章节 + 首图，四次串行请求 |
| 首屏 → 第一页（主机缓存命中、图片磁盘缓存温） | 1091 ms | 省约 2.6 秒 |
| 主机发现本身（有缓存 vs 无缓存） | 16 ms vs 1588 ms | 缓存在 `AppDataLocation/host.txt` |
| 翻到下一页（预取命中） | 59–177 ms | 预取在工作线程完成，不阻塞界面 |

日志格式为 `[  3862 ms] 第 4/285 页 904x1320`（自启动以来的毫秒数），可以直接复现。

**测量边界**：同机同网络；换机器、换网络都会不同。剩余首屏的大头是"详情 → 章节 → 首图"
三次**串行**请求 —— 章节 id 依赖详情，无法并行，这是接口形状决定的，不是没优化。

## 结语

给一个 C++/Qt 客户端加 QML 前端，真正需要事先想清楚的是三件事：

1. **边界**：QML 只用在它独占优势的地方（弹簧手感、条目位移动画），其余留在 Widgets；
2. **方向**：网络与解码一律在工作线程，界面层只转发、不复制业务逻辑；
3. **跨线程的数据**：图像提供器在渲染线程被调用，所以它只能读磁盘缓存，
   而且缓存键必须与写入方逐字一致 —— 为此后端必须把 URL 交给 QML，这不是可选项。

第 3 条我最初以为只是"加个 provider"的细节，实际它是唯一一处
**两个线程通过磁盘共享状态**的地方，值得单独想一遍。
