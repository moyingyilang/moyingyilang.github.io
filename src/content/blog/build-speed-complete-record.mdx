"编译太慢"最容易变成凭感觉的争论。这篇记录把它当成一个可测量的工程问题：
先固定尺子，再按收益逐项改，每项单独对比，并把**没有采用**的方案也写清楚。

## 一、固定测量方法（这步不能省）

- 同一台机器、**同一时刻不跑其它构建**（打包、移动端构建都会抢 CPU）；
- 构建工具命令固定（如一律 `--offline --console=plain`）；
- 记录构建守护进程是冷还是热、是否首次执行；
- 记录**墙上时间**，而不是工具自己报告的耗时；
- 判断"构建是否还在跑"：**不要依赖 `ps`** —— 在未挂载 `/proc` 的容器里它的输出不可信。
  可靠办法是看产物体积/时间戳是否在变化。

## 二、基线：先把现状量出来

| 目标 | 命令 | 基线 |
| --- | --- | --- |
| 桌面端 Kotlin 编译（热） | `gradle compileKotlin` | 4.4 / 4.7 秒 |
| 桌面端打 fat jar（全复用） | `gradle fatJar` | 7.4 秒 |
| 移动端全量（两个 flavor） | `gradle :app:assembleFullRelease :app:assembleLiteRelease` | 10 分 43 秒 |
| 移动端增量 | 同上 | 6.9 秒 |
| 桌面 GUI 无改动增量 | `cmake --build build` | **13~25 秒（每次都要付）** |
| 桌面 GUI 清空重建 | 同上 | 72.5 秒 |
| 单目标打包 | 打包脚本 | 72 秒（其中构建工具仅 2 秒） |
| 单元测试 | `ctest` | 0.33 秒 |

基线本身就有价值：它告诉我们**钱花在哪**。例如打包 72 秒里只有 2 秒是构建工具，
其余是解压运行时 + 压缩 88MB 安装包 —— 这决定了"优化构建脚本"对总时长几乎无影响。

## 三、逐项优化与前后对比

### 1. 打开配置缓存（一行改动，收益明显）

| 命令 | 改前 | 改后 |
| --- | --- | --- |
| `compileKotlin` | 4.4 / 4.7 秒 | **2.0 / 2.7 秒** |
| `fatJar`（全复用） | 7.4 秒 | **2.9 秒** |

关键点：父工程早已开启配置缓存，但**子工程是独立的构建、不继承父配置**。
这类"以为全局配置生效，实际子工程没吃到"的情况，值得优先排查。

### 2. 换构建生成器：从 13 秒到 0.1 秒

Makefile 生成器下，**每次**构建都会重编一个生成源文件（QML 缓存）并重新链接，
哪怕没有任何改动。根因是它的依赖里含类型注册产物，只要上游重跑就整体重跑。
换成 Ninja 后：无改动时 `ninja: no work to do.`，**0.04~0.20 秒**。

这类"每次都重做同一件事"的浪费，通常比"单次编译慢"更值得先解决 —— 因为它乘以你的迭代次数。

### 3. 接入编译缓存（ccache）

| 场景 | 耗时 |
| --- | --- |
| 无 ccache 清空重建 | 72.5 秒 |
| 有 ccache，首次（填充缓存） | **99.4 秒（更慢）** |
| 有 ccache，缓存热 | **13.0 秒** |

**首次变慢**这一点必须如实说明：如果你只构建一次，接入它反而亏。
另一个细节：编译器启动器（`CMAKE_CXX_COMPILER_LAUNCHER`）必须设在 `project()` **之前**才生效。

## 四、没有采用的方案（同样重要）

| 方案 | 为什么不采用 |
| --- | --- |
| 降低安装包压缩级别 | 打包时间显著下降，但产物体积大幅上升 —— 等于拿用户下载量换构建时间 |
| 跨目标复用已解压的运行时 | 解压只占小头，收益有限，徒增脚本复杂度 |
| 打开并行执行 / 调整 worker 数 | 项目此前做过受控 A/B，判定差异落在噪声内（无稳定收益） |
| 禁用守护进程（`--no-daemon`） | 实测更慢：守护进程 7/5 秒 vs 每次新起 JVM 21/14 秒 |
| 多方案一次性全上 | 无法归因，也容易把不稳定因素一起引入 |

## 五、优化之后必须验证功能

速度提升不能以破坏功能为代价。每次改动后我都做了：

- 单元测试全跑（本项目为 16 项，全部通过）；
- **最小功能冒烟**：启动界面并截一张图，确认"能跑起来、能渲染"；
- 发布流程仍然完整可用（版本号一致、产物可校验）。

## 结语

这份记录想传达的是方法而不是数字本身：

1. **先量后改**，并且每项单独测；
2. **优先消除"每次都重复发生"的浪费**（乘以迭代次数后收益最大）；
3. **如实记录"首次更慢"和"没有采用"** —— 否则别人照抄会踩同样的坑。

最终效果：日常迭代的无改动增量构建从 13~25 秒降到 0.1 秒级，清空重建从 72.5 秒降到 13 秒。
