## 46.1 我此前陷入的思维定式

```
❌ 我只在两个方向上来回撞：
   ① 运行时 hook GPU 驱动（vkCmdCopyBufferToImage + vkCmdUpdateBuffer）
   ② 离线替换 .ab 里的字节

⇒ 但这两条都撞到了硬障碍（buffer 大小 / .ab 压缩非标准）
⇒ 说明我该换维度，而不是在同一个维度里加深
```

## 46.2 ★★★★★ 全新视角：从「数据在哪一层」重新划分

```
游戏的数据流：
  .chk 文件（压缩容器）
    ↓ 游戏读 + 解压
  Temp/<uuid> 文件（解压后的资产，游戏 mmap 之）
    ↓ mmap
  进程内存（Unity 对象）
    ↓ il2cpp / libunity
  Vulkan 上传
    ↓
  GPU

⇒ ★ 我一直在【最末端的 Vulkan 层】和【最前端的 .chk 层】动手
⇒ 但【中间三层】我几乎没碰过：
   · Temp 文件层（libc 级！最简单！）
   · 进程内存层（il2cpp 级）
   · libunity 层
```

## 46.3 路径清单（10 条，按我评估的性价比排序）

### ★★★★★ 路径 A：hook Temp 文件的【提取过程】（libc 级）

```
原理：
  · 已知游戏把 .chk 解压到 /sdcard/.../Temp/<uuid>，再 mmap
  · 已知 Temp 文件名是随机 UUID，每次启动重新生成
  · 已知 payload-fdprobe.c 已能 hook open/mmap/pread64（已成功运行过！）

做法：
  ① hook open/openat ⇒ 记录哪个 fd 对应 Temp 文件
  ② hook write/pwrite64（或拦截解压后的数据）⇒
     当写入的字节匹配「目标纹理的压缩数据」时，替换成我们的 BC7
  ③ 或者在 mmap 时：先让游戏正常 mmap，然后把我们的数据【写到那个映射区】

优势：
  · ★ 纯 libc 级，不需要理解 Vulkan 句柄、不需要理解 .ab 格式
  · ★ 我们有现成的 payload-fdprobe.c（已验证能运行）
  · ★ Temp 文件是可写的普通文件（不像 .chk 有完整性校验）
  · ★ 而且 Temp 每次重新生成 ⇒ 不怕被恢复

关键未知：
  · 解压过程用哪些 syscall（write? pwrite? mmap 后直接写？）
  · 目标纹理在 Temp 文件里的偏移

⇒ ★ 这是我目前评估【最高性价比】的新路径
```

### ★★★★★ 路径 B：il2cpp 层的 AssetBundle hook（低频！）

```
原理：
  · 我们已验证 il2cpp 的 RVA hook 可用（XXE1..ctor 成功装上）
  · 游戏加载资产必然经过 il2cpp 的 AssetBundle API
  · 这些 API 是【低频】的（每个资产一次，不是每帧）
  ⇒ 天然避开「高频函数 + 重装竞态」这个我踩了两次的坑！

候选目标（从 dump.cs 取 RVA + 四查序言）：
  · AssetBundle.LoadFromFile / LoadFromMemory
  · AssetBundle.LoadAsset(string) / LoadAssetAsync
  · Texture2D..ctor(int,int,...)
  · Texture2D.LoadImage(byte[])
  · Resources.Load

做法：
  在 LoadAsset 返回前/后，找到目标 Texture2D 对象，
  用 il2cpp API 调 SetPixelData 写入我们的 BC7

优势：
  · 低频 ⇒ 无重装竞态
  · 语义层（能通过 asset 名精确匹配，而不是靠尺寸猜！）
  · 不需要 buffer 大小、不需要 host 指针
```

### ★★★★ 路径 C：重写 .ab 的【单个压缩块】为未压缩（长度保持）

```
原理：
  · Unity AssetBundle 的 LZ4 是【分块】压缩（每块独立）
  · 若某块改成「未压缩」（block type 标志位），则该块内数据明文可见
  · 关键：若未压缩数据长度 ≤ 原压缩块长度，可以用【填充】保持总长度不变
  · ⇒ .blc 的 offset/len 完全不用改！

做法：
  ① 逆向 .ab 的块头格式（找 block size / compression type 字段）
  ② 定位含目标纹理的块
  ③ 解压该块 ⇒ 替换纹理 ⇒ 若结果 ≤ 原块长度，填充到等长；否则拆成多块
  ④ 改块头标志为「未压缩」
  ⑤ 原样写回（长度不变）
  ⑥ blcfix 更新 contentMD5

优势：
  · 完全离线、零运行时风险
  · 不需要重新压缩（避开了 LZ4 压缩器实现）
  · 长度保持 ⇒ 不动 .blc

关键未知：
  · .ab 的块格式（不是标准 UnityFS，需要逆向）
  · 但可以从【最小 .ab（len=2458）】入手逆向，成本可控
```

### ★★★★ 路径 D：KernelSU overlayfs / bind mount 替换文件

```
原理：
  · 设备有 KernelSU（root）
  · 可以用 overlayfs 或 bind mount 把游戏看到的某个文件
    替换成我们准备的版本

做法：
  ① 准备一个「已改好的 .chk」
  ② 用 mount --bind 覆盖原路径（对游戏进程透明）
  ③ 或 overlayfs 只覆盖单个文件

优势：
  · 零代码注入、零 hook、零崩溃风险
  · 修改「持久」且可随时卸载恢复

关键未知：
  · 游戏是否校验 .chk 的 md5（已知 .blc 里有 contentMD5）
    ⇒ 但我们可以同步改 .blc 的 contentMD5（blcfix 已验证可行）
  · /sdcard 是 FUSE（sdcardfs）⇒ bind mount 可能受限
  · 需要 KernelSU 支持 overlay/umount
```

### ★★★★ 路径 E：IFixPatchOut 热修机制（游戏自带的！）

```
关键观察：
  · .blc 里有一个块叫 IFixPatchOut（DAFE52C9，blockType=5，3 个文件）
  · "IFix" = 热修复框架（常见于 Unity 项目）
  · 这个机制【天生就是为了在运行时替换游戏逻辑/资源】

做法：
  ① 研究 IFixPatchOut 的 3 个文件内容与格式
  ② 看它是否支持资源替换（很多热修框架支持 patch 资源）
  ③ 若有 ⇒ 直接用它（游戏官方支持的路径！）

优势：
  · ★ 这是【游戏官方机制】⇒ 最稳定、零崩溃
  · 不需要 hook、不需要逆向压缩格式

关键未知：
  · IFixPatchOut 的文件格式
  · 是否支持纹理资源替换

⇒ ★ 这条被我完全忽略了，值得优先调研！
```

### ★★★★ 路径 F：直接改 Temp 文件（最简单的暴力法）

```
做法：
  ① 游戏启动 ⇒ 等 Temp/<uuid> 生成
  ② 在 Temp 目录里找到含目标纹理的那个文件
  ③ 【直接改那个文件】（它是普通文件，u0_a443 可写）
  ④ 游戏 mmap 的是【改之前】还是【改之后】的内容？
     · 若 mmap 发生在写入之后 ⇒ 改了立刻生效（但游戏已读过一次）
     · 若游戏重新 mmap ⇒ 生效

优势：
  · ★ 极其简单（就是改一个文件）
  · 零注入、零 hook

关键未知：
  · 游戏何时 mmap（改文件必须在 mmap 之前）
  · 可以用「监控 Temp 目录 + 立即改」的方式抢时间窗

⇒ ★ 这个方法值得一试（成本极低）
```

### ★★★ 路径 G：hook libunity.so 的纹理上传（native 层）

```
原理：
  · libunity.so 是 stripped（347 个 dynsym 全是 Android API）
  · 但 libunity 里的 Texture2D 上传函数可以通过【特征码】定位
  · 或通过 il2cpp 的 icall 表（il2cpp 有 icall 注册机制）

做法：
  ① 遍历 il2cpp 的 icall 注册表（运行时）找到 Texture2D 相关 native 函数
  ② hook 它
```

### ★★★ 路径 H：改 Shader/Material 让它用我们的纹理

```
原理：
  · 如果能把材质指向一张我们自己控制的纹理（如某个 UI 纹理）
  · 那就能显示我们的图案
做法：
  · hook 材质绑定的地方（il2cpp 或 Vulkan descriptor set）
难度：高
```

### ★★ 路径 I：修改 APK（用户明确不测）

```
用户约束里写了「E（改 APK）不测」⇒ 排除
```

### ★★ 路径 J：内存搜索 + 直接覆写（逆向工程常用）

```
原理：
  · 游戏启动后，在进程内存里【搜索】目标纹理的特征
  · 找到后直接覆写
做法：
  ① 用 /proc/<pid>/mem 全盘扫描（需要 root）
  ② 找到 512×512 的 BC7 数据位置
  ③ 直接覆写
优势：
  · 不需要任何 hook！
  · 纯 /proc/pid/mem 操作（我们已经会读，写也一样）
关键未知：
  · 如何识别「哪个 512×512 是瞳孔」
  · 但可以【先试试改所有 512×512 的 BC7 块】看效果
⇒ ★ 这是最「暴力」但最简单的方法，而且我们有全部工具（读/写 /proc/pid/mem）
```

## 46.4 ★★★★★ 综合推荐（多解并存，按顺序试）

```
第 1 优先：路径 F（直接改 Temp 文件）—— 成本最低，5 分钟可验证
第 2 优先：路径 E（IFixPatchOut 热修）—— 游戏官方机制，最稳定
第 3 优先：路径 J（内存搜索 + 覆写）—— 纯 mem 操作，无 hook 风险
第 4 优先：路径 A（hook Temp 提取）—— libc 级，payload 已有
第 5 优先：路径 B（il2cpp AssetBundle hook）—— 低频，可精确匹配 asset 名
第 6 优先：路径 C（重写单个压缩块）—— 完全离线
第 7 优先：路径 D（overlayfs）—— 需 KernelSU 支持
```

```
① 我陷入「hook 最末端（GPU）」+「改最前端（.chk）」的两端思维
② 忽略了【中间层】：
   · Temp 文件（libc 级，最简单）
   · 进程内存（/proc/pid/mem）
   · il2cpp 语义层
③ 忽略了【游戏自带的机制】（IFixPatchOut 热修）

# 46.7 ★★★★★ 路径 F 实测：Temp 文件是明文且可写（第 81 轮）

## 46.7.1 ★★★★★ 决定性发现

```
Temp 文件【是解密+解压后的明文】！

证据 1：在 Temp/351eacc5-7c0b-d1d5-0352-cab38979122d (156 MB) 里
        搜到 2 处「512, 512」相邻 int32：
          @ 71,517,775
          @ 102,316,977

证据 2：命中点上下文是【明文 UTF-16 字符串】:
  00 33 00 65 00 63 00 66 00 37 00 63 00 38 00 30   ← "3ecf7c80"
  00 2e 00 61 00 62 00 00                            ← ".ab" + null
  00 26 00 00 / 00 bf 00 00 / 00 a6 02 00 / ...      ← int32 索引表

⇒ 该处是【bundle 清单/索引】，不是 Texture2D 对象
⇒ 但【证明 Temp 文件是明文】—— 这是关键
```

## 46.7.2 ★★★★★ 为什么这条路径最有希望

```
① Temp 文件是【普通可写文件】
     -rw-rw---- u0_a443 ext_data_rw
   ⇒ 不像 .chk 那样有完整性校验（.blc 里有 contentMD5）
   ⇒ 直接覆写不会被检测

② Temp 文件是【明文】
   ⇒ Texture2D 的 m_Width/m_Height/m_ImageData 都可见
   ⇒ 可以直接定位并等长替换

③ Temp 文件【每次启动重新生成】（UUID 命名）
   ⇒ 不存在「被恢复」的问题（下次启动本来就会重建）

④ 不需要任何 hook / 注入
   ⇒ 零崩溃风险
```

## 46.7.3 剩余问题与解法

```
问题：还没定位到纹理数据在 Temp 文件里的确切位置

已知：
  · 该 Temp 文件 156 MB，含 2 处 512,512（在 bundle 索引里）
  · 但也可能含真正的 Texture2D 数据（在别处）

★ 解法（按顺序）：
  ① 搜 Unity SerializedFile 的特征：
     · m_ImageData 前有 4 字节长度 = 262144（00 00 04 00）
     · 已搜到多处 262144（@6689627 等），但要确认哪个后面跟着 262144 字节数据
  ② 用 BC7 的统计特征识别：
     · BC7 每个 16 字节块有固定结构（首字节是 mode）
     · 高熵但非随机
  ③ ★ 最直接：改一个 512×512 的纹理，看游戏画面变化
     · 找到候选位置后，用「纯色」数据覆写（更容易肉眼识别）
  ④ 或者：用「读取即验证」—— 先只读地统计各候选区域的熵与结构

★ 另一个思路：Temp 文件里有 bundle 索引
  ⇒ 索引表里应该有「每个 bundle 的 offset/size」
  ⇒ 解析这个索引 ⇒ 就能定位到具体资源
```

## 46.7.4 下一步（具体）

```
