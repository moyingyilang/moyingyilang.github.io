把界面从一个框架复刻到另一个框架，真正的难点往往不在界面本身，而在下面三个架构问题。
这篇记录我的选择与理由。

## 一、先把"共用层"抽出来

目标项目里同时存在两个前端（传统的窗口部件前端与新的声明式前端），它们都需要：
网络客户端、磁盘与内存缓存、图片解码、以及一个跑在后台线程的工作对象。

如果各自实现一份，会出现两类问题：缓存不共享（同样的图片下两次）、行为漂移
（一边修好的 bug 另一边还在）。所以第一步是把这些抽成一个静态库，两个可执行文件都链接它。

**判断标准很简单**：如果某段代码在两个前端里应当表现完全一致，它就不该出现在前端目录里。

## 二、界面层如何驱动后台工作

网络与解码都是**同步且慢**的操作，放在界面线程会卡住界面。做法是：

1. 工作对象（包含网络客户端）**移入独立线程**；
  注意网络的连接管理器通常要求"在与使用它的线程一致的地方创建"，所以要在工作线程内惰性创建；
2. 界面层只提供**可被声明式界面调用**的方法（把调用排队投递到工作线程），
   并把工作对象的信号**原样转发**给界面；
3. 界面层**不复制任何业务逻辑**：它只做转发。

这里有一条踩过的坑：需要缓存键或 URL 这类信息时，不要试图在界面线程直接访问工作对象的内部状态
（线程归属问题），而应让**工作对象在信号里把它带出来**。

## 三、图片怎么进界面（最容易踩坑的一环）

声明式界面的图片组件通常只接受 URL，而解码后的图像对象在 C++ 侧。可选方案与实际结论：

| 方案 | 结论 |
| --- | --- |
| 自定义图像提供器，按 URL 取图 | 可行，但要注意它是在**渲染线程**被调用的：不能使用界面侧的客户端（线程归属），缓存的内存部分也不是线程安全的。**只用磁盘缓存 + 独立实例**是安全的做法 |
| 直接把图像落成临时文件给 URL | 可行、简单，适合先跑通；代价是每次写盘 |
| 把解码后的图像对象直接塞给界面 | 多数框架不支持，需要自己做桥 |

不管选哪种，**三条硬要求**：

1. **未命中要返回占位图**，不能返回空 —— 否则界面静默空白，用户与开发者都不知道发生了什么；
2. **缓存键要与写入方完全一致**。这一点我踩过：写入方对图片 URL 追加了版本参数用于失效，
   而读取方没有 —— 结果永远命中不了。**不要为了"省事"把版本参数从缓存键里去掉**，
   那会让服务端更新后的图片长期显示旧图，是行为回退而不是优化；
3. **线程归属要写进注释**，否则下一个人会重复踩。

## 四、阶段划分与"什么算完成"

我把移植分成阶段，每个阶段都用**可测量的证据**收尾，而不是"看起来好了"：

- 阶段一：能起窗口并截图（证明渲染链路通）；
- 阶段二：后端桥 + 自检模式，用真实数据核对"列表多少条、章节多少话、一页图片的尺寸"；
- 阶段三：图片进界面，验证"跨实例读到了同一个磁盘缓存"（而不是只验证"返回了一张图"）；
- 阶段四：核心路径的各个界面逐屏复刻，每屏都留截图与日志证据。

**一个实际教训**：有一次我验证"图片显示"时，日志说图片已加载，我就以为完成了；
后来加了一个探针打印**实际绘制尺寸**，才发现它是 `0x0` ——
真实原因是布局只给了容器 2 像素宽。**能测量的中间量比"看起来"可靠得多。**

## 五、诚实记录未验证项

移植过程中必然有一部分无法在本机验证（例如真实图形环境下的对话框交互、
另一个平台的权限行为、真机上的渲染表现）。我的做法是：

- 在项目文档里单列"未验证"清单；
- 每条写清"为什么没法在这台机器验证"与"对方可以怎么验证"；
- 不把"编译通过"当作"功能验证"。

## 结语

移植的架构复杂度主要来自三处：**共用层的边界**、**线程与调用方向**、**数据如何跨越界面边界**。
这三处定清楚之后，剩下的才是"把界面一个个画出来"。
