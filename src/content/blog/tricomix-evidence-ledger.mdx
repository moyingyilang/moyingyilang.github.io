一个多源漫画客户端项目，三个内容源，一套界面。项目做到中途我最怕的不是功能没写完，
而是自己以为写完了：`gradle test` 全绿、APK 装上了、界面能点，于是把「能用」写进文档。

后来我把四类「通过」严格拆开记账。这篇文章就是那本账的口径、内容和踩过的坑。
项目本身开源在 [moyingyilang/TriComiX](https://github.com/moyingyilang/TriComiX)，
下面出现的每个数字都能在那本账里找到出处。

## 一、为什么要有证据账本

先说清楚四类「通过」各自证明了什么。

| 说法 | 实际证明了什么 | 本项目里的反例 |
| --- | --- | --- |
| 编译通过 | 类型与引用对得上 | 章节列表恒为空也能编译通过 |
| 单测通过（合成样本） | 解析逻辑对**给定的输入形状**自洽 | 样本是我自己按猜测写的，和真实页面无关 |
| 真实环境跑通（探针） | 真实响应/页面能被解析，字段名对得上 | EH 取图未带 Referer/UA 时仍算「链路走通」 |
| 真机验证 | 在设备上真的能用 | 探针通过不等于手机上点得动 |

单测用的是自写的合成样本。它能证明的只有一件事：
**解析逻辑对给定形状自洽**。它不能证明**真实页面就是这个形状** ——
样本是照着猜测的键名写的，猜错了，测试和实现会一起错，而且还全绿。

这个项目 168 个单测（JM 56 / Pica 40 / EH 72）加 12 项不联网自检，全部通过。
如果只看这个数字，会以为三个源都能用了。实际情况是：EH 的图片曾经取不到、
Pica 的章节一直是 0、JM 当时还没跑过一次真实请求。这些问题没有一个是单测能发现的。

还有一句话我写在账本开头：

> **不要**把「请求到达了服务端」写成「验证通过」。

请求到达服务端只证明网络通、地址对。响应是不是预期结构、解析出来的字段是不是真的
在页面上，是另一件事。这两件事混在一句「已通过」里，后面每次排查都要重新付一遍学费。

## 二、记账口径：环节 / 证据 / 备注

账本的每一节都是一张三列表格：

| 环节 | 证据 | 备注 |
| --- | --- | --- |
| 搜索 | 返回 20 条真实结果（标题/封面/作者） | 使用者手机上搜索同样正常 |

三条硬规矩：

1. **按「环节 / 证据 / 备注」逐条记**，不写「某源已支持」这种整段结论。
   环节要细到「登录 / 搜索 / 详情 / 章节 / 页列表 / 取图」这个粒度，
   因为出问题的往往正好是其中一环，粗粒度结论会把坏消息盖掉；
2. **拿到真实结果就补一行，含现象**。现象是指可核对的事实：
   「返回 20 条真实结果（标题/封面/作者）」、「页列表 26 页」、
   「第 1 页真实图片地址 `storage-b.picacomic.com/...`」。写「正常」等于没记；
3. **修正也要记**。三处协议差异、一次误报检测、一次根因定位，
   都留在同一份账里，并注明「曾是什么、根因是什么」。
   否则下次看到旧截图，又会以为那就是当时的结论。

账本还给每条证据标了日期。第一天写下的「通过」，第三天可能因站点改版而失效 ——
没有日期的证据，读的人会默认它是今天的事实。

## 三、三源的真实环境证据

以下内容全部是拿真实响应或真实页面核对过的。合成样本之外的这一层，
才是判断「能不能用」的依据。

### Pica（哔咔）

| 环节 | 证据 | 备注 |
| --- | --- | --- |
| 登录 | 探针登录成功；使用者在手机上登录也成功 | 曾是 401/1005，根因是三处协议差异 |
| 搜索 | 返回 20 条真实结果（标题/封面/作者） | 使用者手机上搜索同样正常 |
| 详情 | 标题、作者、标签正确 | 响应是 `data.comic`（单数），不是数组 |
| 章节 | 1 个（`第1話`） | 曾一直是 0，根因见下 |
| 页列表 | 26 页 | — |
| 取图 | 第 1 页真实图片地址 | `storage-b.picacomic.com/...` |

修正过的三处协议差异（三处都曾导致 401/1005）：

1. `nonce` 必须是**固定常量**，不是每请求随机；
2. 必须发 `User-Agent`（`okhttp/3.8.1`）；
3. `app-build-version` 应为 **45**（原用 44），且 `app-uuid` 用固定值
   （`defaultUuid`）、`Content-Type` 所有请求都带。

另经逐字核对：`api-key` 与 HMAC 密钥与完整客户端完全一致。

### EH（E-Hentai）

| 环节 | 证据 | 备注 |
| --- | --- | --- |
| 搜索 | 25 条真实结果，标题/封面/作者/时间/页数/标签全对 | 曾因「按单元格取值」而取不到封面与作者 |
| 详情 | 标题、作者、标签、章节 1 | 作者取自 `/uploader/` 链接（`#gj` 元素实际为空） |
| 页列表 | 189 页 | 另有一部 141 页的长作品，分批取页后全部带 imgkey |
| 取图 | 第 1 页原图地址（`fullimg/...png`） | — |

抓真实页面之后钉死的结构事实（这些都不可能从合成样本里猜到）：

- 列表是 `table.itg.gltc`，四列 `分类 | 缩略图+时间 | 标题 | 上传者`；
  时间是 `postedpop_<gid>`；**缩略图与上传者不在标题单元格里**；
  `gl1e/gl3e/gl3t/gl5t` 属于另一种布局，在真实 `gltc` 里出现 0 次；
- 详情页 `#gj` 为空，用户名在 `/uploader/<名字>` 链接里；
- 图片页顶部那个 `<img>` 是**界面图标**，内容图**带 `style`**，
  原图藏在 `Download original` 链接里。

### EH 长作品分批取页

用定向探针打在一部 **141 页**的作品上：

| 检查 | 结果 |
| --- | --- |
| 详情页 | 141 页、token 解析正常、首批内联 20 个 imgkey |
| 旧的 `gtoken`（api.php 方法） | 请求第 21-23 页与第 1-3 页返回同样的 `Invalid page.` 错误 |
| 结论 | 不是页段问题，而是该方法在新版站点已失效 |
| 现行做法验证 | `?p=0/1/2` 分别给出第 1-20 / 21-40 / 41-60 页的 imgkey |
| 修复后 | 走源接口 `pages()`：141 页全部带 imgkey，末页取图成功 |

失效的 `gtoken` 解析器与它的测试一起删掉了 ——
留着会让人以为「还有另一条可用路径」，这是账本最怕的误导。

### JM

| 环节 | 证据 | 备注 |
| --- | --- | --- |
| 搜索 | 探针 45 条真实结果 | 真机另测通过 |
| 详情 | 详情与标签正确 | 同上 |
| 真机 | 使用者实测可用 | 此前修掉三处：图源需主机发现、单篇作品用作品 id 当章节、反切片参数与缓存键 |

## 四、仍未被真实环境覆盖的部分

这张表比上面那张更重要。它是账本里唯一能防止我自我感觉良好的部分。

| 项 | 状态 | 说明 |
| --- | --- | --- |
| EH 登录 | 未实测 | 表单与 cookie 已实现并有单测，但没在真实环境登过 |
| EH 收藏读 | 未实测 | 已实现，未在真实环境取过 |
| EH 收藏写 | 未接 | 接口已扩 `FAVORITE_WRITE`，JM 源已实现，EH 未接 |
| 会话跨重启 | **不支持** | 令牌与 cookie 只活在运行内存里，重启需重新登录 |
| Pica 首页与历史 | **不实现** | 端点在任何可得资料中都不存在 |
| EH 历史 | **不实现** | 历史是客户端本地功能，服务端没有对应端点 |
| 界面搬迁 | 未完成 | `JmNavHost` 主体、`HomeScreen` 完整布局、下拉刷新与上拉加载更多、双指缩放 |

「未实测」这一档还有个副产品：它让「能力显隐」有了依据。
界面只按 `Capability` 决定入口显隐，源不具备的能力直接剪掉入口或显示「该源不支持」，
不保留点了没反应的控件。

## 五、「明确不支持」与「未验证」是两类

一开始我把这两类混着写，结果读者（包括几天后的我自己）会把它们理解成同一件事。
现在它们是两个字段：

| 类别 | 判据 | 做法 |
| --- | --- | --- |
| 明确不支持 | 接口端点在**任何可得资料里都不存在** | 不编地址，宁可返回 `Unsupported` |
| 未验证 | 端点或实现存在，但没在真实环境跑过 | 写「未实测」，附上已实现到什么程度 |

Pica 的首页与历史属于第一类：我把 6 篇存档文档与两个公开参照实现都翻过，
没有找到端点。**没有找到就不猜地址** —— 猜出来的地址在客户端里看起来很像能用的代码，
是最贵的一种假象。

EH 的历史属于同一类，但理由不同：它是**客户端本地功能**，
不该由源实现。这类东西放错层，会在界面里表现为「这个源不支持历史」，
而真实情况是「历史本来就不该问源要」。语义放错地方的代价，和写错地址是一样的。

## 六、一处自我更正：`hath` 检测方式的误报

账本里我留了一条对自己的更正，因为它是「探针显示也要能取信」这个教训的源头。

先前探针输出「含 hath: false」，我据此以为图片地址里没有 `hath`。**这是错的**：

- 真实地址形如 `https://<随机主机>.hath.network:53342/h/…`，
  `hath` **嵌在主机名里**，不是查询参数；
- 我的检测按 `?hath=` 去找，所以误报为「没有」。

取图功能本身不受影响（地址原样使用，能取到图），但探针与界面上那一行显示是**误导性的**：
它给出了一个看起来精确、实际会把人带偏的结论。

教训是：**探针的显示本身也在被验证的范围内**。
一个「false」如果没有写清楚它在检测什么，就会被我当成事实收进结论。
从那以后我给自己加了一条：探针输出的每一项都要能说清判据，
否则那一项不该出现在结论里，只能出现在原始日志里。

## 七、环境坑清单

这个项目的构建环境比协议本身更消耗时间。下面每一条都实际卡过进度。

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| `aapt2 ... Syntax error` | AGP 从 Maven 拉的 aapt2 是 x86_64 | 用 `android.aapt2FromMavenOverride` 指向本机 build-tools 里的 arm64 版 |
| release 包缺 manifest | aarch64 + arm64 aapt2 下资源优化会产出空资源表 | 关闭 AGP 的资源优化步骤 |
| `git push` 报权限错或「不存在」 | 主机 DNS 只返回 IPv6，且没有 IPv6 路由 | 从容器解析出 IPv4，用 `GIT_SSH_COMMAND="ssh -o HostName=<ip> -p 443" git push` |
| 容器连不上外网（超时） | 容器网络经 tun0 出口，**时通时不通** | JVM 加 `-Djava.net.preferIPv4Stack=true`；失败多为瞬时，重试即可 |
| 容器里看不到项目文件 | bind 挂载会掉 | 重新挂载（项目目录与 SDK、`.android` 同理） |
| 文件写入失败 / 文件被清空 | 本机 `/tmp` 不可写 | 临时文件一律放项目内目录，不碰 `/tmp` |

最后一条不是「小麻烦」。我因为 `/tmp` 不可写，用重定向拼接的方式把一个文档
**清空后提交并推送**了，只能重建。这条坑写在清单里，也写在下面的教训里。

## 八、过程教训

逐条都带现象，因为不带现象的教训下次还是会犯。

1. **多行 `sed`/`perl` 替换在本机极不可靠**。本会话失败近十次，
   多因花括号、斜杠与 `$` 的转义。可靠做法是**整体重写文件**，
   或用 `\Q…\E` 加不同分隔符，或先打印上下文再精确替换。
   失败的表现很隐蔽：命令返回成功，文件却是半改状态。
2. **写完文件必须验证产物**。就是上面那次：重定向把一个文档清空，
   我没看产物就提交推送。现在的动作是「写完立刻读一遍产物」，
   而不是「命令没报错就算写成」。
3. **「编译通过」不等于「语义完整」**。Pica 的章节一直为空，
   根因是 `detail()` 里写死 `chapters = emptyList()`。
   编译发现不了，单测也发现不了（合成样本里没有章节），
   只有真机或探针链路能暴露。
4. **超时 ≠ 协议错**。先区分「HTTP 000 超时」与「服务端返回错误码」，再下结论。
   本会话多次把网络超时误判成协议问题，浪费了不少轮次。
5. **别把猜测当事实**。我早先写过「EH 的解析被污染、在这个环境不可能通」，
   后来证明那只是瞬时的网络状态。猜测一旦进了结论，
   后面所有推理都建在沙子上。

## 九、每步的固定动作

节奏固定下来之后，返工明显变少。每改动一次：

1. 编译；
2. 跑 168 个单测；
3. 构建并装包；
4. 核对 `git status`；
5. 都对了才提交。

第 3 步有个坑值得单独写：**构建失败时，「安装成功」装的是旧包**。
本会话踩过两次 —— 看到 `pm install` 输出成功，就以为新改动生效了，
实际设备上跑的还是上一个版本的 APK。所以必须**先看构建结果，再看安装结果**，
两步不能合成一句「已更新」。

探针的用法也固定成两条路子：

```bash
# 不联网自检（12 项，不需要账号）
probe.sh eh "" 1 selfcheck

# 真实链路（EH 免登录；Pica 需登录，密码走环境变量，避免进入进程列表）
probe.sh eh "关键词" 1 full
TRICOMIX_PASS='…' probe.sh pica "关键词" 1 full 账号
```

密码用环境变量传，是为了不让它出现在进程列表里。同理，
账本与文章里出现的凭据一律只写占位符形式：

```bash
export TRICOMIX_PICA_APIKEY=…
export TRICOMIX_PICA_SIGNINGKEY=…
```

探针在每一步失败时会输出**失败的环节**与错误类别（`Unsupported` / `Unknown` / `Parse`），
不会把失败表示成空结果。这一条很关键：空列表看起来像「这个源没内容」，
而实际上可能是登录态过期或站点改版。

## 十、账本自己也会过期

写这篇文章时我回头核对了全部文档，发现同一份账本里有两处自相矛盾：

| 矛盾 | 位置 A | 位置 B |
| --- | --- | --- |
| 某源是否实测 | 一处写该源**未实测** | 同一份文档另一处又写该源**真机实测通过** |
| 滑动翻页是否实现 | 一处写滑动翻页**未实现**（未搬入） | 另一处与状态文档又写**已实现**左右滑动翻页 |

两处都不是笔误那么简单，而是「更新了结论、没更新旧句」的典型后果：
文档分节按时间追加，新结论写在后面，前面的旧句没人回去改。

处理办法有三条，我写进了账本本身：

- **以最新提交的状态文档为准**。冲突时，按提交时间取最近的那条，
  并在文中如实写明存在冲突，而不是悄悄选一个；
- **旧结论要回改，不只追加**。追加是省事的，但它会让同一个问题有两个答案；
- **每次提交前扫一遍被自己改动的结论是否还在别处出现**。

这条经验对博客文章同样成立：文章里的「已验证」也有保质期。
所以我把每个数字和日期都写在正文里，而不是只写一句「目前可用」。

## 十一、可以直接抄走的部分

如果只带走一句话，就是这句：**把「我改了代码」和「它在真实环境里能用」分成两件事记。**

- 四条清单固定为：编译 / 单测 / 真实环境 / 真机，逐条给证据，缺项就写缺项；
- 证据写现象（条数、页数、字段名、地址形态），不写形容词；
- 「未验证」和「明确不支持」分成两栏，前者写已实现到什么程度，后者写端点在资料里不存在；
- 单测通过只说明解析逻辑对给定形状自洽，不能替代真实响应核对；
- 探针与界面的显示也在被验证的范围内，一句 `false` 必须能说清判据；
- 构建失败时的「安装成功」是旧包，先看构建再看安装。

这套记账没有让项目变快，它做的是另一件事：**让我知道自己到底站在哪里**。
在一个三源、跨协议、环境还处处漏水的项目里，这个「知道」比任何一次编译通过都值钱。
